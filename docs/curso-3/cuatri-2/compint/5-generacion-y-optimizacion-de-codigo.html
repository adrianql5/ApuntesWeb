5. Generación y Optimización de Código · COMPINT

![Nota] Estos apuntes no están muy bien, sirven para responder los ejercicios típicos que pone el rivera en el examen pero no desglosan los conceptos para poder entender todo bien. Es que estaba quemado ya de currar este cuatri y me dio excesiva pereza la parte del rivera.

5.1 Bloques básicos

Un bloque básico es una secuencia de instrucciones que se ejecuta seguida.

Cumple:

1. Solo se entra por la primera instrucción.
2. Solo se sale por la última.
3. No hay saltos a instrucciones intermedias.

Para encontrarlos, buscas líderes:

1. La primera instrucción es líder.
2. Todo destino de salto es líder.
3. La instrucción justo después de un salto también es líder.

Ejemplo:

1: b = 0
2: a = c + d
3: b = a + e
4: d = a + b
5: p = d
6: b = c + d
7: if (b == 0) goto 13
8: if (b > 0) goto 2
9: a = b + c
10: *r = a
11: b = d + e
12: goto 1
13: *r = *r + a
14: return

Líderes:

1  → primera instrucción y destino de goto 1
2  → destino de goto 2
8  → instrucción después del salto de la línea 7
9  → instrucción después del salto de la línea 8
13 → destino del goto 13

Bloques:

B1 = {1}
B2 = {2,3,4,5,6,7}
B3 = {8}
B4 = {9,10,11,12}
B5 = {13,14}

5.2 Variables vivas y siguiente uso

Una variable está viva si su valor se va a usar más adelante.

El siguiente uso es la próxima línea donde se usará.

Ejemplo:

1: t = a + b
3: x = t * c

Después de la línea 1:

t está viva
siguiente uso de t = 3

Tu profesor usa una tabla con dos datos por variable:

v  = viva
nv = no viva
número = siguiente uso
0 = no hay siguiente uso dentro del bloque

Cómo se hace la tabla

Para una instrucción:

x = y op z

vas de abajo hacia arriba.

En cada línea haces:

1. Apuntas el estado actual.
2. Matas x:
   x = nv, 0

3. Marcas y y z:
   y = v, línea actual
   z = v, línea actual

Para una condición:

if (b == 0) goto 13

solo se usa b, así que:

b = v, línea actual

Ejemplo

Bloque:

2: a = c + d
3: b = a + e
4: d = a + b
5: p = d
6: b = c + d
7: if (b == 0) goto 13

Si no te dan más información global, tus apuntes dicen que se suele asumir:

Variables no temporales vivas al salir.
Temporales no vivas al salir.

Aquí todas parecen variables normales, así que puedes empezar suponiendo vivas al salir:

a b c d e p
v v v v v v
0 0 0 0 0 0

Ahora recorres desde abajo.

Línea 7:

if (b == 0) goto 13

Usa b.

b = v, 7

Línea 6:

b = c + d

Antes de modificar, b estaba viva con uso 7.
Luego matas b, y marcas c y d con uso 6.

Línea 5:

p = d

Matas p, marcas d con uso 5.

Línea 4:

d = a + b

Matas d, marcas a y b con uso 4.

Y así sucesivamente.

El formato final sería parecido al de tu profesor:

Salida:
      a   b   c   d   e   p
      v   v   v   v   v   v
      0   0   0   0   0   0

7:
      a   b   c   d   e   p
      v   v   v   v   v   v
      0   7   0   0   0   0

6:
      a   b   c   d   e   p
      v   nv  v   v   v   v
      0   0   6   6   0   0

5:
      a   b   c   d   e   p
      v   nv  v   v   v   nv
      0   0   6   5   0   0

No hace falta memorizar la tabla: memoriza la regla de matar la definida y marcar los operandos.

5.3 DAG / GDA de un bloque básico

Un DAG o GDA es un grafo que representa los cálculos de un bloque.

Sirve para:

- detectar subexpresiones comunes
- eliminar código muerto
- ver dependencias entre instrucciones
- reordenar instrucciones si se puede

Cómo se construye:

1. Creas hojas para los valores iniciales de variables.
2. Cada operación crea un nodo.
3. Los hijos del nodo son las últimas definiciones de sus operandos.
4. El nodo se etiqueta con la variable que acaba de definirse.

Ejemplo:

1: a = b + c
2: d = a - e
3: x = b + c

DAG:

b0    c0
 \    /
  +        etiqueta: a, x
  |
  a/x

a/x   e0
 \    /
  -        etiqueta: d

La línea 3 no crea un nodo nuevo porque b + c ya estaba calculado. Se reutiliza el mismo nodo.

5.4 DAG con punteros

Ejemplo:

1: u = a + b
2: t = b + c
3: *p = t
4: a = a * b
5: t = a + c
6: a = 2 * t
7: a = a / u

Caso A: el compilador sabe que p no apunta a ninguna variable usada

Entonces:

*p = t

es una escritura indirecta, pero no invalida los nodos de a, b, c, u, t, etc.

El DAG se puede seguir construyendo normalmente.

Textualmente:

n1 = a0 + b0        etiqueta: u
n2 = b0 + c0        etiqueta: t

n3 = *=(p0, n2)     efecto lateral: *p = t

n4 = a0 * b0        etiqueta: a
n5 = n4 + c0        etiqueta: t
n6 = 2 * n5         etiqueta: a
n7 = n6 / n1        etiqueta: a

Lo importante es:

La línea *p = t no destruye el DAG anterior
porque sabemos que p no toca esas variables.

Caso B: el compilador NO sabe a qué apunta p

Entonces *p = t puede modificar cualquier variable.

Por tanto:

*p = t

se considera una barrera.

En tus apuntes aparece esta idea: una asignación indirecta *=, si no se sabe a qué puede apuntar, elimina los nodos construidos hasta ahora.

Entonces el DAG se corta en dos partes.

Primera parte:

n1 = a0 + b0        etiqueta: u
n2 = b0 + c0        etiqueta: t
n3 = *=(p0, n2)

Después de *p = t, empiezas casi desde cero:

n4 = a1 * b1        etiqueta: a
n5 = n4 + c1        etiqueta: t
n6 = 2 * n5         etiqueta: a
n7 = n6 / u1        etiqueta: a

Uso a1, b1, c1, u1 para indicar “valor nuevo/desconocido después de la escritura indirecta”.

Si no sabemos a qué apunta p, la instrucción *p = t puede modificar cualquier variable accesible, por tanto invalida los nodos anteriores del DAG.

5.5. DAG con arrays

Ejemplo:

1: a = b + c
2: b = a - d
3: d = x[k]
4: x[j] = b
5: c = x[k]
6: c = c + d
7: e = b / c

Regla principal:

Una escritura en un array puede cambiar lecturas posteriores del mismo array.

La línea 3 lee:

d = x[k]

La línea 4 escribe:

x[j] = b

La línea 5 vuelve a leer:

c = x[k]

¿Podemos reutilizar la lectura de la línea 3 para la línea 5?

No, salvo que sepamos que:

j != k

Porque si j = k, entonces la línea 4 modifica justo x[k].

Por tanto:

d = x[k]
x[j] = b
c = x[k]

normalmente genera dos lecturas distintas de x[k].

Representación:

d = x[k]     → nodo =[](x, k), etiqueta d
x[j] = b     → nodo []=(x, j, b), modifica x
c = x[k]     → nuevo nodo =[](x, k), etiqueta c

5.6 Descriptores de registros y variables

Esto se usa con obtenReg.

Un descriptor de registro dice qué variables están actualmente en cada registro.

Ejemplo:

R1: d
R2: a, t
R3: u, v

Significa:

R1 contiene el valor actual de d
R2 contiene el valor actual de a y t
R3 contiene el valor actual de u y v

Un descriptor de variable dice dónde está el valor actual de cada variable.

Ejemplo:

a: R2
d: R1
t: R2
u: R3
v: R3

5.7 Ejercicio típico: traducir b = v

Situación:

R1: d
R2: a, t
R3: u, v

Queremos traducir:

b = v

Como v ya está en R3, no hace falta generar ningún LD.

Y como es una copia, no hace falta instrucción máquina. Solo actualizamos descriptores:

Antes:

R3: u, v

Después:

R3: u, v, b

Y el descriptor de b pasa a ser:

b: R3

Respuesta de examen:

No se genera ninguna instrucción.
Se actualizan descriptores:
R3 = {u, v, b}
b = {R3}

Si al final del bloque b está viva y no está en memoria, entonces más tarde habría que hacer:

ST b, R3

Pero para la operación b = v, no se emite código.

5.8 Qué usa obtenReg

¿Qué usa la función obtenReg para decidir?

Respuesta:

- Los descriptores de registros.
- Los descriptores de direcciones o variables.
- La información de vida.
- La información de siguiente uso.
- La instrucción concreta que se está traduciendo.

La idea es escoger registros intentando evitar ST innecesarios.

Si una variable de un registro:

- ya está guardada en memoria,
- no se va a usar más,
- o va a ser sobrescrita,

entonces puedo reutilizar ese registro sin almacenar.

Si no, tengo que hacer un derrame:

ST variable, R

5.9 Coste de LD R1, *8(R2)

Criterio 1: coste Aho / longitud de instrucción

Regla:

coste = 1 + coste de los modos de direccionamiento

  • Registro R1: coste adicional 0.

  • Dirección indirecta con desplazamiento *8(R2): suele contar desplazamiento 8 y acceso indirecto.

Resultado típico:

Coste = 3

Criterio 2: accesos a memoria

Aquí miras cuántos accesos a memoria provoca.

Para:

LD R1, *8(R2)

se accede a una dirección calculada a partir de 8 + contenido(R2) y luego se obtiene el contenido indirecto.

En clase normalmente se razona también como:

Coste = 3

5.10 Reglas de reensamblado

El reensamblado es volver del DAG a código de tres direcciones.

Reglas importantes:

1. Un nodo debe generarse después de sus hijos.
2. Una escritura en array debe respetar el orden respecto a lecturas/escrituras anteriores del mismo array.
3. Una lectura de array debe ir después de escrituras anteriores que puedan afectarla.
4. Una instrucción no debe cruzar una escritura por puntero si puede cambiar su valor.
5. Si un nodo tiene varias variables vivas adjuntas, hay que generar copias.

Ejemplo:

a = b + c
d = b + c

DAG:

n1 = b + c, etiquetas {a, d}

Si a y d están vivas al salir, al reensamblar necesitas:

a = b + c
d = a

o al revés.

Porque ambas variables necesitan conservar ese valor.
