3.1 Punto de partida: peticiones, respuestas y endpoints

Antes de las reglas del tema conviene tener claro el vocabulario básico, porque todo lo demás se apoya en él.

Una API (Application Programming Interface) es la "puerta" que un programa ofrece para que otros programas lo usen. En una API REST, esa puerta funciona sobre HTTP, el mismo protocolo que usa tu navegador: un cliente (una app móvil, una web, otro servicio) envía una petición y el servidor devuelve una respuesta.

Una petición HTTP tiene cuatro partes:

  • Verbo (o método): qué quieres hacer (GET obtener, POST crear, PUT/PATCH modificar, DELETE borrar).
  • URL: sobre qué recurso lo quieres hacer (/aulas/12).
  • Cabeceras: metadatos (quién eres, en qué formato envías o quieres los datos).
  • Cuerpo (opcional): los datos que envías, normalmente en JSON.

La respuesta tiene un código de estado (un número que dice cómo fue: 200 bien, 404 no existe...), cabeceras y, opcionalmente, un cuerpo con los datos.

POST /aulas HTTP/1.1                     ← verbo + URL
Host: api.etse.gal
Content-Type: application/json           ← cabeceras
Authorization: Bearer eyJhbGciOi...

{ "nome": "Aula 3", "capacidade": 20 }   ← cuerpo

HTTP/1.1 201 Created                     ← código de estado
Location: https://api.etse.gal/aulas/15  ← cabeceras
Content-Type: application/json

{ "id": 15, "nome": "Aula 3", "capacidade": 20 }   ← cuerpo

Un endpoint es simplemente la combinación de un verbo y una URL que la API ofrece para hacer una operación concreta. GET /aulas (listar aulas) y POST /aulas (crear un aula) son dos endpoints distintos aunque compartan URL. Diseñar una API es decidir qué endpoints existen y qué recibe y devuelve cada uno.

Analogía: la carta de un restaurante

La API es la carta: te dice qué puedes pedir y cómo. Cada endpoint es un plato de la carta ("POST /reservas" = "reservar mesa"). La petición es lo que le dices al camarero, con tus datos (el cuerpo: "para 4, a las 21:00"). La respuesta es lo que te traen, y el código de estado es lo que te dice el camarero: "marchando" (201), "no queda" (404), "esa zona es solo para socios" (403).

Dos palabras más: un recurso es cualquier "cosa" identificable (un aula, una reserva) y una colección es el conjunto de recursos del mismo tipo (todas las aulas). En la URL, /aulas es la colección y /aulas/12 es un recurso concreto.

3.2 El servicio y su ciclo de vida

Como vimos en el tema 2, un servicio es un componente de negocio con una interfaz bien definida, autónomo, desacoplado y con un objetivo limitado: por ejemplo, listar todas las películas de una plataforma de streaming u obtener los detalles de un libro de una biblioteca.

Los servicios web tienen un ciclo de vida de cuatro fases:

  1. Análisis y diseño: identificar qué servicios necesita la organización y definir formalmente sus interfaces (el "contrato"), incluidos los requisitos no funcionales como la seguridad, el rendimiento y el nivel de servicio esperado.
  2. Desarrollo e implementación: programar el servicio, eligiendo las tecnologías que permitan cumplir los requisitos anteriores.
  3. Despliegue y gestión: poner el servicio en producción con técnicas de automatización como CI/CD (Integración/Despliegue Continuo) y monitorizar constantemente su salud, por ejemplo para escalar o desescalar instancias.
  4. Retiro y obsolescencia: al final de su vida útil, el servicio debe retirarse de forma planificada para minimizar el impacto en los consumidores, ya sea sustituyéndolo por una nueva versión o con una retirada gradual y comunicada de antemano.

3.3 Servicios sin estado (stateless)

Una de las características más importantes de REST es la ausencia de estado: el servidor no guarda información sobre las peticiones anteriores de un cliente para poder resolver una nueva. Cada petición es autocontenida: lleva toda la información necesaria para que el servidor la ejecute por sí sola.

Esto simplifica mucho el diseño y el escalado, porque reduce el acoplamiento entre llamadas sucesivas: cualquier servidor puede atender cualquier petición, así que la carga se reparte fácilmente, y los resultados son consistentes y repetibles sin importar el orden o la máquina que los procese.

Analogía: el cajero que no te conoce

Un servicio con estado es como un camarero que recuerda lo que pediste antes ("¿lo de siempre?"): si ese camarero se va, el siguiente no sabe nada. Un servicio sin estado es como una máquina expendedora: cada vez le das el producto y el dinero completos, y da igual qué máquina uses. Por eso es fácil poner diez máquinas en lugar de una.

3.4 Recursos y URLs

Las APIs REST se organizan en torno a recursos. Un recurso es cualquier entidad (o colección de entidades) lo bastante importante como para ser identificada y referenciada por sí misma: un documento, un registro de una base de datos o el resultado de una operación. La única restricción es que tiene que poder referenciarse mediante una URL.

3.4.1 Anatomía de una URL

Una URL es el identificador para acceder a un recurso, y debería comunicar claramente a qué recurso se refiere sin necesidad de abrirla. Todas siguen el formato del RFC 3986:

URL=<esquema>://<autoridad>/<ruta>[?<consulta>]
Parte Qué define Ejemplo en https://api.biblioteca.gal:8443/libros?page=2
Esquema (scheme) El protocolo, normalmente https (o http) https
Autoridad (authority) El dominio del servidor (el proveedor); puede incluir un puerto api.biblioteca.gal:8443
Ruta (path) La ruta jerárquica hasta el recurso /libros
Consulta (query) Parámetros opcionales para filtrar, paginar, ordenar... page=2

3.4.2 Reglas de diseño de URLs

Estas reglas son las que se aplican al diseñar los endpoints en los ejercicios:

Regla ✅ Bien ❌ Mal
Siempre en minúsculas https://api.biblioteca.gal/libros HTTPS://API.BIBLIOTECA.GAL/LIBROS, https://api.biblioteca.gal/LIBROS
Guiones (-) para separar palabras, no guiones bajos /libros/le-petit-prince /libros/le_petit_prince, /libros/le+petit+prince, /libros/lepetitprince, /libros/le%20petit%20prince
Colecciones con sustantivo en plural /libros /libro
Recursos individuales: la colección + identificador único /libros/le-petit-prince, /produtos/123 —
Sin verbos en la URL: la operación la dice el verbo HTTP GET /libros /getlibros, /libros/obter_libros, /libros/consultar, /libros/ver-todos
Sin barra final /libros /libros/
Filtrado, paginación y ordenación en la query, nunca en el path /libros?page=2&size=5 /libros/2/5, /libros/page/2/size/5

Una idea útil: el path identifica QUÉ recurso y la query dice CÓMO lo quieres (filtrado, orden, página). Si un dato identifica un recurso concreto (su id), va en el path; si solo acota o modifica el resultado, va en la query.

3.5 Verbos HTTP

Las APIs REST usan los verbos HTTP para indicar la operación sobre los recursos, de forma parecida a las operaciones de una base de datos (crear, leer, actualizar, borrar).

3.5.1 Idempotencia y seguridad

Una operación es idempotente si ejecutarla una o varias veces con la misma petición produce el mismo efecto en el servidor. Ojo: no garantiza que la respuesta sea la misma (el código de estado puede cambiar), sino que el estado del recurso no cambia más allá de la primera ejecución.

Una operación es segura si no causa ningún cambio en el servidor: es de solo lectura, así que puedes llamarla cuantas veces quieras sin miedo a modificar los datos.

GET POST PUT PATCH DELETE QUERY
Idempotente ✅ ❌ ✅ ❌ ✅ ✅
Seguro ✅ ❌ ❌ ❌ ❌ ✅

Por qué cada uno:

  • GET solo lee: es seguro y, por tanto, también idempotente.
  • PUT es idempotente porque, aunque lo envíes varias veces con el mismo contenido, el recurso acaba siempre igual.
  • DELETE es idempotente porque, tras borrar en la primera llamada, las siguientes no hacen nada, pero el recurso sigue borrado (la respuesta puede pasar de 204 a 404, pero el estado del servidor es el mismo).
  • POST no es idempotente: cada llamada crea un recurso nuevo; llamarlo dos veces crea dos pedidos distintos.
  • PATCH no es idempotente porque, según la lógica del servidor, ejecutarlo varias veces puede dar resultados distintos (por ejemplo, "añade un autor a la lista" añade uno más cada vez).
  • Ninguno de los que modifican (POST, PUT, PATCH, DELETE) es seguro.

Analogía: el interruptor y el botón del ascensor

PUT es como poner el interruptor en "encendido": da igual cuántas veces lo hagas, la luz queda encendida (idempotente). POST es como echar una moneda en una hucha: cada vez hay una moneda más (no idempotente). GET es como mirar la luz: no cambia nada (seguro).

3.5.2 Guía de uso de cada verbo

Verbo Para qué Sobre qué se aplica Cuerpo de la petición Ejemplo
GET Recuperar la representación de un recurso o colección Colecciones y recursos concretos Nada GET /produtos, GET /produtos/123
POST Crear un recurso nuevo. Excepcionalmente, consultas complejas que no caben en la URL Solo colecciones (añades un elemento a la colección) La representación del recurso a crear POST /produtos
PUT Sustituir por completo un recurso Solo recursos concretos La representación completa del recurso modificado PUT /produtos/123
PATCH Modificar parcialmente un recurso Solo recursos concretos Una lista de instrucciones de cambio (JSON Patch) PATCH /produtos/123
DELETE Eliminar un recurso (o una colección) Normalmente recursos concretos; sobre colecciones es posible pero peligroso y poco habitual Nada DELETE /produtos/123
QUERY Recuperar datos, como GET, pero con una consulta compleja en el cuerpo Colecciones La consulta QUERY /libros

La diferencia entre PUT y PATCH cae mucho en los exámenes: con PUT mandas el recurso entero tal como debe quedar (si omites un campo, se entiende que lo quieres vacío); con PATCH mandas solo las instrucciones de lo que cambia.

3.5.3 PATCH y JSON Patch

El cuerpo de un PATCH es un array de operaciones en formato JSON Patch (RFC 6902). Cada operación tiene op (qué hacer: add, replace, remove, test, copy, move), path (qué campo) y value (el nuevo valor, si hace falta). La petición se envía con Content-Type: application/json-patch+json.

[
  { "op": "add",     "path": "/authors/0", "value": "Miguel de Cervantes Saavedra" },
  { "op": "replace", "path": "/edition",   "value": "500 Aniversary Edition" }
]

Añade un autor en la primera posición de la lista authors y sustituye el valor del campo edition.

3.5.4 QUERY

QUERY sirve, como GET, para recuperar datos, pero permite incluir información en el cuerpo de la petición, lo que lo hace ideal para consultas complejas. Es seguro e idempotente. Según las diapositivas, antes de su estandarización (2026) estas consultas se hacían con POST, que no es ni seguro ni idempotente.

El cuerpo puede usar distintos lenguajes de consulta. Todos estos piden "título, autor e ISBN de los libros de precio menor que 10 y categoría fantasía o ciencia ficción":

Lenguaje Consulta
JSON Path $[?(@.price < 10 && (@.category == 'fantasy' || @.category == 'sci-fi'))]['title','author','isbn']
JMES Path [?price < `10` && (category == 'fantasy' || category == 'sci-fi')].{title: title, author: author, isbn: isbn}
Mongo Query Language {"filter": {"price": {"$lt": 10}, "category": {"$in": ["fantasy","sci-fi"]}}, "projection": {"title":1,"author":1,"isbn":1}}
OASIS OData {"$select": ["title","author","isbn"], "$filter": "price lt 10 and (category eq 'fantasy' or category eq 'sci-fi')"}
SQL (from-less) SELECT title, author, isbn WHERE price < 10 AND category IN ('fantasy','sci-fi');
Otros SPARQL, GraphQL, PRQL...

3.6 Problemas de diseño habituales

Las diapositivas plantean tres problemas típicos que no encajan a la primera en REST, con su solución.

¿Cómo hacer idempotente un POST? Si el cliente repite un POST (por ejemplo, porque se cortó la red y no sabe si llegó), se crearían dos recursos. La solución es incluir en la petición una clave de idempotencia (idempotency key) para deduplicar llamadas. El cliente debe enviar siempre la misma clave para la misma petición y nunca repetirla en peticiones distintas; el servidor guarda las claves y, antes de procesar una petición, comprueba si esa clave ya está en el sistema y en qué estado.

Analogía: el número de ticket

Es como el número de un pedido en un restaurante de comida rápida: si vuelves a la caja con el mismo número, no te cobran otra hamburguesa, te dicen "ese pedido ya está hecho".

¿Cómo ejecutar tareas asíncronas o de larga duración? (por ejemplo, generar un informe que tarda minutos). Se hace un POST para crear un recurso "tarea" que permita monitorizar la ejecución. Después, cuando el cliente hace GET de esa tarea: mientras no haya terminado (o si ha fallado), se devuelve la representación de la tarea con su estado; si ha terminado bien, se devuelve una redirección a la URL del resultado. (Aunque las diapositivas no lo detallan, lo habitual es responder al POST con 202 Accepted y redirigir con 303 See Other.)

¿Cómo soportar la ejecución de funciones o métodos? (algo que es más una acción que una "cosa"). Se representa la función como un recurso (por ejemplo, calcular una ruta entre dos sitios: /routes) y se hace un GET pasando los parámetros en la query: GET /routes?from=Santiago&to=Lugo. Así se evita meter verbos en la URL (/calcular-ruta).

3.7 Códigos de estado HTTP

Las APIs REST usan los códigos de estado estándar de HTTP para notificar el resultado de una operación. Son una señal clara y legible por máquinas para que el cliente reaccione adecuadamente.

3.7.1 Categorías

Categoría Significado
1XX – Informativos La petición está en proceso. Poco comunes en APIs REST
2XX – Éxito La petición se procesó correctamente
3XX – Redirecciones El cliente debe hacer alguna acción adicional (por ejemplo, ir a otra URL)
4XX – Error del cliente Hay un error en la petición: el cliente debe modificarla para que sea válida
5XX – Error del servidor Falló el servidor al procesarla, aunque la petición fuera correcta

3.7.2 Reglas de uso

Minimizar los 5XX que llegan al cliente. Los 5XX son errores del servidor sobre los que el cliente no puede hacer nada. Por eso el servidor debe tratar las excepciones y, siempre que sea posible, devolver el 4XX adecuado, que el cliente sí puede corregir. La mayoría de errores que vea un cliente deberían ser 4XX.

Usar siempre el código más específico posible. 200 OK y 400 Bad Request son genéricos y aportan poca información; 400 solo se usa cuando no hay un 4XX más específico. Los códigos concretos que hay que conocer:

Código Cuándo se usa
200 OK Éxito genérico cuando no se crea ni se elimina nada (p. ej., un GET)
201 Created Se creó un recurso (POST). Debe incluir la cabecera Location con la URL del nuevo recurso
204 No Content Éxito con cuerpo intencionadamente vacío (p. ej., tras un DELETE o una actualización sin devolver nada)
400 Bad Request Error genérico del cliente, cuando no hay otro más preciso (JSON mal formado, parámetros inválidos)
401 Unauthorized Error de autenticación: faltan las credenciales o son incorrectas. "No sé quién eres"
403 Forbidden Error de autorización: credenciales correctas, pero sin permiso para ese recurso u operación. "Sé quién eres, pero no puedes"
404 Not Found El recurso no existe
406 Not Acceptable El servidor no puede responder en ninguno de los formatos que el cliente pide en Accept
409 Conflict La petición choca con el estado actual del recurso (p. ej., reservar un aula ya reservada a esa hora)
422 Unprocessable Entity La petición está bien formada pero sus datos no pasan la validación (p. ej., capacidad negativa)
429 Too Many Requests El cliente ha hecho demasiadas peticiones en poco tiempo

(Las diapositivas enumeran 406, 409, 422 y 429 como ejemplos de códigos específicos; la descripción de cada uno es la estándar de HTTP.)

Dos distinciones que se preguntan mucho:

401 frente a 403. El 401 es un problema de autenticación (no has demostrado quién eres o lo has hecho mal); el 403 es de autorización (se sabe quién eres, pero no tienes permiso). Un alumno sin iniciar sesión que intenta crear un aula → 401; un alumno identificado que intenta crear un aula (solo para administradores) → 403.

204, 404 y 200 con lista vacía. 204 No Content: el cuerpo está vacío a propósito. 404 Not Found: el recurso no existe. 200 OK con []: la colección sí existe, pero ningún elemento cumple el filtro (por ejemplo, GET /produtos?categoria=inexistente), así que se devuelve una lista vacía, que no es lo mismo que no devolver nada.

3.8 Cabeceras y cuerpo de los mensajes

Además del código de estado, un mensaje HTTP tiene cuerpo y cabeceras. El cuerpo contiene la representación en texto del recurso o colección, en formatos como JSON, XML, CSV o YAML; el estándar de facto es JSON, por su ligereza y legibilidad. Las cabeceras son metadatos: contienen lo necesario para que la comunicación funcione, sin formar parte del contenido.

3.8.1 Media types

Como el cuerpo puede venir en muchos formatos, hay que identificar en cuál está. Para eso están los Media Types (o tipos MIME), que estandarizan cómo nombrar un formato y se usan en la negociación de contenidos. Su forma completa es:

tipo/subtipo+sufijo;paraˊmetros
  • Tipo: la categoría general (text, image, audio, video, application, multipart...). Debe ser una de las definidas por la IANA.
  • Subtipo: el formato concreto. Puede ser estándar (html, json, txt) o propietario de una aplicación (application/vnd.app.user, application/vnd.ms-word, application/vnd.openxmlformats-officedocument.wordprocessingml.document).
  • Sufijo: indica que el subtipo se basa en un formato más conocido y sigue su sintaxis: application/json-patch+json, application/hal+json, application/problem+json (todos son JSON "por debajo").
  • Parámetros: información extra: text/html;charset=utf8, application/vnd.app.user;version=2.

3.8.2 Tipos de cabeceras

Tipo Cabecera Qué indica
De contenido (metadatos del cuerpo) Content-Type Formato de los datos del cuerpo (application/json)
Content-Length Tamaño del cuerpo
Content-Language Idioma del contenido
De negociación (cliente y servidor acuerdan el formato) Accept Formatos que el cliente acepta en la respuesta (Accept: application/json)
Accept-Language Idiomas que prefiere el cliente (Accept-Language: gl, es-ES;q=0.9)
Accept-Encoding Algoritmos de compresión que entiende el cliente
De autenticación y autorización Authorization Credenciales o token del cliente para acceder a recursos protegidos
De enlaces (autodescubrimiento) Location En la respuesta a un POST (201), URL del recurso creado
Link Enlaces a recursos relacionados; es uno de los principios de HATEOAS (Hypermedia as the Engine of Application State), una forma avanzada de diseñar APIs REST
De caché Cache-Control Controla la caché (edad máxima, prohibir guardar...)
Expires Fecha y hora en que caduca la copia en caché
Age Segundos que lleva el recurso en caché

La pareja que más confunde: Content-Type dice en qué formato va lo que envío; Accept dice en qué formato quiero lo que me respondas.

3.8.3 Reglas para modelar peticiones y respuestas

  • Soportar JSON siempre por defecto. Otros formatos (XML, CSV) son recomendables para sistemas antiguos, pero opcionales.
  • Sin envoltorios adicionales: el cuerpo debe ser directamente el recurso. En vez de { "data": { "nome": "Exemplo" } }, se devuelve { "nome": "Exemplo" }; así el cliente lo procesa más fácil.
  • Usar siempre Content-Type, en petición y respuesta. Puede ser genérico (application/json) o específico de la aplicación (application/vnd.gal.usc.etse.User+json), lo que permite negociar contenido y versionar la API.
  • Enlaces a sí mismos: toda respuesta de un recurso debería incluir un enlace a él mismo, para que la API sea autodescubrible y el cliente no tenga que conocer toda su estructura.
  • Location en los recursos nuevos: al crear con POST (201 Created), devolver en Location la URL completa del recurso creado, para que el cliente acceda a él sin construir la URL.

3.9 Manejo de errores

Los errores son inevitables en una API pública, así que su gestión debe ser minuciosa y estar bien documentada. Hay que minimizar los 5XX (tratando las excepciones y devolviendo el 4XX adecuado) y, como los códigos se quedan cortos (un 400 puede significar un campo que falta, un valor inválido, un formato incorrecto...), acompañar el código con un cuerpo que explique qué falló y por qué. Así el cliente puede tratar los errores de forma programática.

El formato estándar es el RFC 7807: Problem Details for HTTP APIs, un JSON con estos campos:

Campo Contenido
type Enlace a la documentación del tipo de error (un código más específico)
title Título corto y legible que resume el error
status El código HTTP usado (p. ej., 400)
detail Descripción larga y específica del problema
instance Identificador único de esta ocurrencia concreta, para rastrearla en los logs
errors (Opcional) Lista de errores detallados si hay varios problemas 
{
  "type": "https://api.empresa.com/docs/erros/validación",
  "title": "A petición contén campos non válidos",
  "status": 400,
  "detail": "Un ou máis campos da petición non pasaron a validación. Verifique os detalles a continuación.",
  "instance": "a6b7c8d9-e0f1-2345-6789-abcd0123ef45",
  "errors": [
    { "field": "correo", "message": "O formato do correo non é válido" },
    { "field": "contrasinal", "message": "O contrasinal debe ter polo menos 8 caracteres" }
  ]
}

3.10 Ejercicios resueltos

3.10.1 Método para resolver un ejercicio de diseño de API

Los ejercicios de examen piden, para cada funcionalidad, URL, verbo, descripción, parámetros/cuerpo y a veces cabeceras y códigos. Se resuelven siempre con los mismos pasos:

  1. Busca los sustantivos del enunciado: son los recursos. Nómbralos en plural como colecciones (/aulas, /reservas, /usuarios). Si uno "pertenece" a otro, se puede anidar: /proxectos/{id}/tarefas.
  2. Traduce la acción a un verbo HTTP: consultar → GET; crear → POST (sobre la colección); modificar todo → PUT; modificar una parte → PATCH; eliminar/cancelar → DELETE (sobre un recurso concreto).
  3. Decide path o query: si el dato identifica un recurso concreto (su id), va en el path (/aulas/{id}); si filtra, pagina u ordena, va en la query (?capacidade-min=10).
  4. Cuerpo: solo en POST (el recurso a crear), PUT (el recurso completo) y PATCH (instrucciones JSON Patch). GET y DELETE no llevan cuerpo.
  5. Cabeceras: Authorization si hace falta estar identificado; Content-Type si envías cuerpo; Accept si esperas cuerpo en la respuesta.
  6. Códigos: el de éxito según el verbo (GET → 200, POST → 201 + Location, PUT → 200, PATCH → 200 o 204, DELETE → 204) y los errores típicos (400/422 datos malos, 401 sin identificar, 403 sin permiso, 404 no existe, 409 conflicto).
  7. Repasa las reglas de URL: minúsculas, guiones, plural, sin verbos, sin barra final.

3.10.2 Ejercicio 1: aulas de estudio de la ETSE

Enunciado. La ETSE quiere modernizar la gestión de sus aulas de estudio, que hoy es manual, con una API REST para alumnos y administradores. Debe permitir consultar aulas disponibles por capacidad o fecha, reservar franjas horarias para grupos, consultar las reservas propias, cancelar una reserva y, para administración, gestionar el catálogo de aulas. Para cada funcionalidad hay que indicar URL, verbo, descripción y parámetros/cuerpo, siguiendo el formato del ejemplo:

URL Verbo Descripción Parámetros/Cuerpo
/libros POST Añadir un nuevo libro al catálogo Cuerpo: { "titulo": "...", "autor": "..." }

Análisis. Los sustantivos son aulas, reservas y usuarios (alumnos): tres colecciones, /aulas, /reservas y /usuarios. Las reservas se crean, se consultan por alumno y se cancelan por sí mismas, así que tienen su propia colección.

Solución:

# URL Verbo Descripción Parámetros / Cuerpo
1 /reservas POST Crear una nueva reserva de un aula para un grupo Cuerpo: { "aulaId": 12, "usuarioId": 345, "data": "2026-10-15", "horaInicio": "10:00", "horaFin": "12:00", "numeroPersoas": 4 }
2 /aulas GET Consultar las aulas que cumplen ciertos criterios de búsqueda Query: ?capacidade-min=4&data=2026-10-15&hora-inicio=10:00&hora-fin=12:00 (todos opcionales; también page, size)
3 /aulas/{id} GET Consultar los detalles de un aula concreta Path: id del aula. Sin cuerpo
4 /usuarios/{id}/reservas GET Consultar las reservas activas de un alumno concreto Path: id del alumno. Query: ?estado=activa
5 /reservas/{id} DELETE Cancelar una reserva existente Path: id de la reserva. Sin cuerpo
6 /aulas POST Crear una nueva aula (administración) Cuerpo: { "nome": "Aula de estudo 3", "edificio": "ETSE", "capacidade": 20, "equipamento": ["proxector", "encerado"] }
7 /aulas/{id} PUT Modificar los datos de un aula existente (sustitución completa) Path: id. Cuerpo: la representación completa del aula { "nome": "...", "edificio": "...", "capacidade": 25, "equipamento": [...] }

Por qué cada decisión:

  1. Crear → POST sobre la colección /reservas. Los datos de la reserva van en el cuerpo. Respondería 201 Created con Location: /reservas/{nuevoId}.
  2. Buscar con criterios → GET sobre la colección, con los criterios en la query porque filtran, no identifican. Sería un error poner /aulas/capacidade/4/data/2026-10-15 (filtros en el path) o /buscar-aulas (verbo en la URL). Si no hay aulas que cumplan el filtro: 200 OK con [], no 404.
  3. Detalle → GET sobre un recurso concreto: el id identifica, así que va en el path.
  4. Reservas de un alumno → las reservas "pertenecen" al alumno, así que se anida: /usuarios/{id}/reservas. El "activas" filtra, por eso va en la query. Una alternativa igual de válida es GET /reservas?usuario={id}&estado=activa.
  5. Cancelar → DELETE sobre la reserva concreta, sin cuerpo; respondería 204 No Content. Si se quisiera conservar el historial de reservas canceladas, otra opción válida es cambiar su estado con PATCH /reservas/{id} y el cuerpo [{"op": "replace", "path": "/estado", "value": "cancelada"}].
  6. Crear aula → igual que la 1, POST sobre /aulas. Al ser solo para administración, un alumno identificado recibiría 403 Forbidden.
  7. Modificar → PUT si se envían todos los datos del aula; si solo se quisieran cambiar algunos campos (por ejemplo, la capacidad), PATCH /aulas/{id} con JSON Patch.

3.10.3 Ejercicio 2: "ProXecto Áxil"

Enunciado. Una startup quiere una API REST para su servicio de gestión de proyectos en equipo, "ProXecto Áxil", que consumirán apps web y móviles. Los usuarios autenticados deben poder gestionar las tareas de sus proyectos. Hay que diseñar 5 endpoints indicando todos estos elementos: URL, verbo, descripción, parámetros (query o cuerpo, con los campos principales), cabeceras que debe enviar el cliente y códigos de estado de éxito y de error más comunes.

  1. Crear una tarea dentro de un proyecto, validando que el usuario tiene permisos en él.
  2. Consultar las tareas de un proyecto, pudiendo filtrar por estado.
  3. Actualizar parcialmente una tarea: solo su estado, ningún otro campo.
  4. Consultar el detalle de una tarea por su identificador único.
  5. Eliminar una tarea, comprobando que el usuario es administrador del proyecto.

Análisis. Los recursos son proyectos y tareas, y cada tarea pertenece a un proyecto, así que las tareas se anidan: /proxectos/{proxectoId}/tarefas. Como "los usuarios autenticados" son los únicos que pueden usar la API, todas las peticiones llevan Authorization, y en todas pueden aparecer 401 (sin token o token inválido), 403 (sin permiso en ese proyecto) y 404 (el proyecto o la tarea no existen).

Solución resumida:

# URL Verbo Parámetros / Cuerpo Cabeceras Éxito Errores
1 /proxectos/{proxectoId}/tarefas POST Cuerpo: titulo, descricion, estado, responsableId, dataLimite Authorization, Content-Type: application/json, Accept: application/json 201 Created + Location 400/422, 401, 403, 404
2 /proxectos/{proxectoId}/tarefas GET Query: ?estado=en-curso (opcional; también page, size) Authorization, Accept: application/json 200 OK (lista, puede ser []) 400, 401, 403, 404
3 /proxectos/{proxectoId}/tarefas/{tarefaId} PATCH Cuerpo JSON Patch: [{"op":"replace","path":"/estado","value":"completada"}] Authorization, Content-Type: application/json-patch+json 200 OK (tarea actualizada) o 204 400, 401, 403, 404, 422
4 /proxectos/{proxectoId}/tarefas/{tarefaId} GET Path: ids. Sin cuerpo Authorization, Accept: application/json 200 OK 401, 403, 404
5 /proxectos/{proxectoId}/tarefas/{tarefaId} DELETE Path: ids. Sin cuerpo Authorization 204 No Content 401, 403, 404

Detalle de cada operación:

1. Crear una tarea

POST /proxectos/42/tarefas
Authorization: Bearer <token>
Content-Type: application/json
Accept: application/json

{ "titulo": "Deseñar a base de datos", "descricion": "Modelo E-R inicial",
  "estado": "pendente", "responsableId": 7, "dataLimite": "2026-10-20" }

Se crea con POST sobre la colección de tareas del proyecto. Si va bien: 201 Created con Location: /proxectos/42/tarefas/128 y la tarea creada en el cuerpo. Errores: 400 Bad Request si el JSON está mal formado; 422 Unprocessable Entity si falta el título o la fecha no es válida; 401 sin token; 403 si el usuario no tiene permisos en ese proyecto (la validación que pide el enunciado); 404 si el proyecto 42 no existe.

2. Consultar las tareas de un proyecto

GET /proxectos/42/tarefas?estado=en-curso
Authorization: Bearer <token>
Accept: application/json

GET sobre la colección, y el filtro por estado en la query porque filtra. Éxito: 200 OK con la lista; si ninguna tarea tiene ese estado, 200 OK con [] (la colección existe, no es un 404). Errores: 400 si el valor de estado no es válido; 401, 403 (no es miembro del proyecto), 404 (el proyecto no existe).

3. Actualizar solo el estado de una tarea

PATCH /proxectos/42/tarefas/128
Authorization: Bearer <token>
Content-Type: application/json-patch+json

[ { "op": "replace", "path": "/estado", "value": "completada" } ]

Es una modificación parcial, así que el verbo es PATCH (no PUT, que exigiría mandar la tarea entera). El servidor debe rechazar cualquier operación cuyo path no sea /estado, porque el enunciado prohíbe cambiar otros campos: en ese caso responde 422 Unprocessable Entity (la petición está bien formada, pero no es aceptable). Éxito: 200 OK con la tarea actualizada (o 204 No Content si no se devuelve cuerpo). Otros errores: 400 si el JSON Patch está mal formado, 401, 403, 404.

4. Consultar el detalle de una tarea

GET /proxectos/42/tarefas/128
Authorization: Bearer <token>
Accept: application/json

GET sobre el recurso concreto, con el identificador en el path. Éxito: 200 OK con la tarea completa. Errores: 401, 403, 404 si la tarea no existe. Como el enunciado dice que el identificador es único, también sería válido GET /tarefas/128; lo importante es ser coherente en todo el diseño.

5. Eliminar una tarea

DELETE /proxectos/42/tarefas/128
Authorization: Bearer <token>

DELETE sobre el recurso concreto, sin cuerpo. Éxito: 204 No Content. Errores: 401 sin token; 403 si el usuario no es administrador del proyecto (la comprobación que pide el enunciado: es un problema de autorización, no de autenticación); 404 si la tarea no existe.

En estos ejercicios **no hay una única respuesta correcta**: se valora que el diseño **respete las reglas** (recursos en plural, sin verbos en la URL, filtros en la query, verbo y código adecuados) y que sea **coherente**. Si eliges una alternativa, justifícala en una línea.

3.11 Ideas clave

  • Endpoint = verbo + URL. Petición: verbo, URL, cabeceras, cuerpo. Respuesta: código, cabeceras, cuerpo.
  • Ciclo de vida: análisis y diseño → desarrollo → despliegue y gestión (CI/CD, monitorización) → retiro planificado.
  • Stateless: cada petición lleva todo lo necesario; cualquier servidor puede atenderla → fácil de escalar.
  • URL = esquema://autoridad/ruta?consulta. Reglas: minúsculas, guiones, colecciones en plural, recurso = colección + id, sin verbos, sin barra final, filtros/paginación/orden en la query.
  • Idempotentes: GET, PUT, DELETE, QUERY. Seguros: GET, QUERY. POST y PATCH no son ni una cosa ni otra.
  • POST solo sobre colecciones (crea); PUT sustituye entero; PATCH modifica parcialmente con JSON Patch (application/json-patch+json); GET/DELETE sin cuerpo.
  • Problemas: POST idempotente → idempotency key; tareas largas → recurso "tarea" + GET de su estado/redirección; funciones → recurso + GET con query.
  • Códigos: 201 + Location al crear, 204 cuerpo vacío, 200 + [] si el filtro no encuentra nada (no 404), 401 autenticación vs 403 autorización, 409 conflicto, 422 validación. Minimizar 5XX y usar el código más específico.
  • Media type: tipo/subtipo+sufijo;parámetros. Content-Type = formato de lo que envío; Accept = formato que quiero recibir.
  • Errores con RFC 7807 (type, title, status, detail, instance, errors).
