P.1 Spring y Spring Boot

P.1.1 Qué es Spring

Programar aplicaciones empresariales en Java era tradicionalmente complejo y lleno de código repetitivo (boilerplate). Spring es un ecosistema (no solo un conjunto de bibliotecas) pensado para crear aplicaciones robustas, escalables y fáciles de mantener con mucho menos esfuerzo. Su "superpoder" son dos principios: la Inversión de Control (IoC) y la Inyección de Dependencias (DI).

Normalmente, si una clase necesita otra, la crea ella misma con new. Con IoC se invierte esa responsabilidad: es Spring (su "contenedor") quien crea y guarda los objetos que la aplicación necesita, llamados beans. Con DI, cada clase simplemente declara qué necesita y Spring se lo entrega ya creado. Así las clases no dependen de cómo se construyen sus dependencias: el código queda más modular, flexible y fácil de probar.

Analogía: el chef y el restaurante (la de los apuntes) Sin Spring, eres un chef que tiene que ir al mercado a comprar cada ingrediente antes de cocinar. Con **IoC**, el restaurante (el contenedor de Spring) se encarga de comprar los ingredientes (los beans); tú solo dices cuáles necesitas. La **DI** es el mecanismo por el que el restaurante te los deja directamente en tu cocina.

La inyección se hace con anotaciones (etiquetas que empiezan por @ y que Spring lee) como @Component o @Autowired, o por configuración:

java

@Service // Un "bean" de servicio gestionado por Spring
public class ServizoVendas {
    @Autowired // Spring inyecta aquí el repositorio, no hace falta hacer "new"
    private RepositorioVendas repositorioVendas;

    public Double calcularTotal(Long idFactura) {
        return repositorioVendas.findFacturaById(idFactura).getTotal();
    }
}

Para entenderlo mejor [Qué es la inyección de dependencias en Spring Boot](https://www.youtube.com/watch?v=z40otl4g_kM) — el concepto con un ejemplo práctico (vídeo, 5:40).

P.1.2 Spring Boot

Si Spring es el motor, Spring Boot es la llave que arranca el coche: una extensión que simplifica muchísimo la configuración y la puesta en marcha. Su filosofía es "convención sobre configuración": toma decisiones sensatas por ti para que no tengas que configurarlo todo a mano. Sus características clave:

  • Servidor embebido: la aplicación se empaqueta en un único .jar ejecutable que incluye su propio servidor web (Tomcat o Jetty), así que se ejecuta en cualquier sitio sin instalar un servidor aparte.
  • Configuración automática: analiza las dependencias del proyecto y configura sola la mayoría de componentes; por ejemplo, si ve Spring Data JPA, prepara la conexión con la base de datos.
  • Starters: dependencias preconfiguradas; spring-boot-starter-web, por ejemplo, ya trae todo lo necesario para una aplicación web RESTful.

P.1.3 Arquitectura en capas

Organizar la aplicación en capas separa responsabilidades. En Spring lo habitual son tres capas, que se comunican entre sí mediante inyección de dependencias:

Capa Anotación Responsabilidad
Presentación o web (Controller) @RestController La interfaz pública: recibe las peticiones HTTP y delega en el servicio. No debe tener lógica de negocio
Negocio o servicio (Service) @Service El corazón: reglas de negocio y coordinación de operaciones. Usa el repositorio para obtener datos y les aplica la lógica
Acceso a datos (Repository) @Repository Habla con la base de datos: leer, escribir, actualizar, borrar. Con Spring Data, muchas operaciones se obtienen solo definiendo una interfaz

Analogía: la oficina de correos El **controller** es la ventanilla: recoge tu petición y te da la respuesta, pero no decide nada. El **service** es la oficina de dentro, que aplica las normas ("¿tiene sello?, ¿pesa demasiado?"). El **repository** es el almacén donde se guardan los paquetes.

P.1.4 El ecosistema de Spring

  • Spring Data: simplifica el acceso a datos, tanto SQL como NoSQL.
  • Spring Security: el estándar de la industria para la seguridad en Java.
  • Spring Cloud: herramientas para aplicaciones distribuidas y microservicios.
  • Spring Batch: procesamiento por lotes de grandes volúmenes de datos.

P.1.5 Crear un proyecto con Spring Initializr

La forma más rápida de empezar es Spring Initializr (start.spring.io), una web que genera el esqueleto del proyecto:

  1. Entra en https://start.spring.io.
  2. Configura el proyecto: Project (el gestor de dependencias, Maven o Gradle; en estos apuntes, Gradle - Groovy, ver P.1.6), Language (normalmente Java), versión de Spring Boot (la última estable; las marcadas como SNAPSHOT o M están en desarrollo) y los metadatos: Group (tu organización, p. ej. com.meuempresa), Artifact (nombre del proyecto, p. ej. meu-primeiro-proxecto), Name, Description, Package name (paquete base de las clases), Packaging (Jar para una aplicación autocontenida) y versión de Java (p. ej., 21 LTS).
  3. Añade las dependencias con ADD DEPENDENCIES, la parte más importante. Como mínimo: Spring Web (para las APIs REST) y el Spring Data de tu base de datos. Para un proyecto con PostgreSQL como el de estos apuntes: Spring Web, Spring Data JPA, PostgreSQL Driver y Validation (y, si quieres, Docker Compose Support; ver P.2.5). Qué es cada una se explica en P.1.6.
  4. Pulsa GENERATE y descarga el .zip.
  5. Descomprímelo y ábrelo en tu IDE, que reconocerá el proyecto Maven/Gradle e importará las dependencias.

Referencias de los apuntes: la documentación oficial de Spring Framework, Spring Boot y las guías de Spring, y los tutoriales de Baeldung (introducción, tutorial, Spring vs Spring Boot).

P.1.6 Gradle: el gestor de dependencias

Una dependencia es una librería hecha por otros que tu proyecto necesita para funcionar: Spring Web para atender peticiones HTTP, el driver de PostgreSQL para hablar con la base de datos, Jackson para convertir objetos a JSON... Antiguamente había que descargar cada librería (un .jar) a mano, copiarla al proyecto y buscar a su vez las librerías que ella necesitaba, con el riesgo de mezclar versiones incompatibles.

Un gestor de dependencias (o herramienta de construcción, build tool) automatiza todo eso: tú escribes en un fichero qué librerías necesitas y él las descarga de un repositorio público (normalmente Maven Central), descarga también las que ellas necesitan (dependencias transitivas) y las deja listas para el compilador. Además compila, ejecuta los tests y empaqueta la aplicación en el .jar. En Java los dos más usados son Maven (fichero pom.xml, en XML) y Gradle (fichero build.gradle, más corto y legible). Hacen lo mismo; en estos apuntes se usa Gradle.

Analogía: la lista de la compra `build.gradle` es tu **lista de la compra**. No vas tú a cada tienda: le das la lista a Gradle, que lo compra todo y se acuerda de traer también lo que cada cosa necesita (si pides "tarta", trae harina y huevos). Lo comprado se guarda en una despensa (la caché `~/.gradle/caches`), así que la segunda vez no vuelve a la tienda.

El fichero build.gradle

En Spring Initializr elige Gradle - Groovy, que es la sintaxis de los ejemplos de estos apuntes (la variante Kotlin genera un build.gradle.kts con una sintaxis algo distinta). El fichero generado tiene esta forma (no lo copies: usa el que te generó Initializr, que lleva las versiones correctas):

gradle

plugins {
    id 'java'
    id 'org.springframework.boot' version '...'          // la versión de Spring Boot elegida
    id 'io.spring.dependency-management' version '...'   // elige versiones compatibles por ti
}

group = 'com.meuempresa'
version = '0.0.1-SNAPSHOT'

java {
    toolchain { languageVersion = JavaLanguageVersion.of(21) }   // versión de Java
}

repositories {
    mavenCentral()          // de dónde se descargan las librerías
}

dependencies {              // la "lista de la compra"
    implementation 'org.springframework.boot:spring-boot-starter-web'
    implementation 'org.springframework.boot:spring-boot-starter-data-jpa'
    runtimeOnly 'org.postgresql:postgresql'
    testImplementation 'org.springframework.boot:spring-boot-starter-test'
}

tasks.named('test') {
    useJUnitPlatform()      // los tests se ejecutan con JUnit 5
}

Cada dependencia se identifica por sus coordenadas grupo:artefacto:versión. Las de Spring no llevan versión porque el plugin io.spring.dependency-management sabe qué versión de cada librería es compatible con tu Spring Boot y la pone por ti. Las librerías que Spring no gestiona, como json-patch (P.7), sí necesitan la versión explícita: 'com.github.java-json-tools:json-patch:1.13'.

Muchas dependencias de Spring son starters (P.1.2): paquetes que agrupan varias librerías. spring-boot-starter-web, por ejemplo, trae Spring MVC, el servidor Tomcat y Jackson. Puedes ver el árbol completo de lo que se descarga con ./gradlew dependencies.

Tipos de dependencia

La palabra que va delante de las coordenadas indica cuándo se necesita la librería:

Configuración Cuándo se usa Ejemplo
implementation Para compilar y ejecutar. La más habitual Los starters de Spring
runtimeOnly Solo al ejecutar: tu código no la usa directamente El driver de PostgreSQL (lo usa Hibernate, no tú)
compileOnly + annotationProcessor Solo al compilar; no va en el .jar Lombok
developmentOnly Solo mientras desarrollas (IDE o bootRun); no va en el .jar final DevTools, Docker Compose Support
testImplementation Solo para los tests spring-boot-starter-test

Dependencias habituales en un proyecto como este

En Initializr Línea en build.gradle Para qué sirve
Spring Web implementation 'org.springframework.boot:spring-boot-starter-web' Controladores REST, Tomcat embebido y Jackson (P.3, P.8)
Spring Data JPA implementation 'org.springframework.boot:spring-boot-starter-data-jpa' JPA + Hibernate + repositorios (P.4)
PostgreSQL Driver runtimeOnly 'org.postgresql:postgresql' Conectar con PostgreSQL
Validation implementation 'org.springframework.boot:spring-boot-starter-validation' Hibernate Validator: @NotBlank, @Valid... (P.9)
Docker Compose Support developmentOnly 'org.springframework.boot:spring-boot-docker-compose' Arranca el docker-compose.yml junto con la app (P.2.5)
Spring Boot DevTools developmentOnly 'org.springframework.boot:spring-boot-devtools' Reinicia la app sola al guardar cambios
Lombok compileOnly y annotationProcessor 'org.projectlombok:lombok' Genera getters, setters y constructores con anotaciones (@Getter, @Setter...)
Spring Data MongoDB implementation 'org.springframework.boot:spring-boot-starter-data-mongodb' Si usas MongoDB en lugar de SQL (algunos ejemplos de P.5 y P.6)
H2 Database runtimeOnly 'com.h2database:h2' Base de datos en memoria, sin instalar nada; útil para tests
(no está en Initializr) implementation 'com.github.java-json-tools:json-patch:1.13' JSON Patch (P.7)
(siempre incluida) testImplementation 'org.springframework.boot:spring-boot-starter-test' JUnit, Mockito y utilidades de test

Los nombres exactos pueden variar según la versión de Spring Boot (por ejemplo, Spring Boot 4 reorganizó algunos starters). Si Initializr te genera nombres algo distintos a los de esta tabla, quédate con los que te genera.

Añadir dependencias más tarde

No hace falta regenerar el proyecto: añade la línea en el bloque dependencies y recarga Gradle en el IDE (en IntelliJ, el icono del elefante Load Gradle Changes; en VS Code, Java: Reload Projects). Un truco para no equivocarte con las coordenadas: en Initializr, añade la dependencia y pulsa EXPLORE; te muestra el build.gradle resultante y puedes copiar la línea exacta.

El wrapper y los comandos de Gradle

El proyecto incluye los ficheros gradlew, gradlew.bat y la carpeta gradle/wrapper/. Son el wrapper: un pequeño script que descarga la versión correcta de Gradle la primera vez, así que no necesitas instalar Gradle y todo el equipo usa la misma versión. Hay que subirlos a Git. Las carpetas build/ y .gradle/, en cambio, se generan solas y ya vienen excluidas en el .gitignore de Initializr.

Comando Qué hace
./gradlew bootRun Arranca la aplicación
./gradlew build Compila, pasa los tests y genera el .jar en build/libs/
./gradlew test Ejecuta solo los tests
./gradlew clean Borra la carpeta build/
./gradlew dependencies Muestra el árbol de dependencias

En Windows se usa gradlew.bat bootRun (cmd) o .\gradlew bootRun (PowerShell). El .jar generado se ejecuta con java -jar build/libs/nombre.jar. En el día a día, normalmente basta con el botón Run del IDE, que por debajo hace lo mismo.

P.2 Docker: la base de datos en un contenedor

Antes de programar el acceso a datos (P.4) hace falta una base de datos funcionando. En lugar de instalar PostgreSQL en tu ordenador, lo habitual es ejecutarlo con Docker: un comando y lo tienes, siempre con la misma versión y configuración, y sin "ensuciar" tu sistema.

P.2.1 Docker, máquinas virtuales, Kubernetes y la nube

Son cuatro términos que se oyen juntos pero resuelven problemas distintos:

Tecnología Qué es Cuándo se usa
Máquina virtual (VM) Simula un ordenador completo, con su propio sistema operativo entero, dentro del tuyo. Muy aislada, pero pesada (gigas de disco, minutos en arrancar) Cuando necesitas otro sistema operativo completo: un Windows en un Mac, un servidor Linux de pruebas
Docker (contenedores) Empaqueta un programa con todo lo que necesita (librerías, configuración) y lo ejecuta aislado, compartiendo el núcleo del sistema de tu máquina. Ligero: arranca en segundos Ejecutar servicios (una base de datos, tu propia app) igual en cualquier máquina. Es lo que necesitas en esta práctica
Kubernetes Un orquestador: gestiona muchos contenedores repartidos en muchas máquinas. Decide dónde va cada uno, los reinicia si se caen y lanza más copias si hay mucho tráfico Empresas con decenas o cientos de contenedores en producción. Para un proyecto de clase no hace falta
AWS (y Azure, Google Cloud) Alquilar infraestructura de otros: servidores, bases de datos, almacenamiento. Dentro puedes tener VMs (EC2), contenedores (ECS, o Kubernetes con EKS) o una base de datos ya gestionada (RDS) Cuando quieres desplegar tu aplicación en internet sin tener servidores propios. No es una alternativa a las anteriores, sino el sitio donde se ejecutan

Analogía: la mudanza **Docker** es una **caja estándar de mudanza**: metes dentro lo que sea y se transporta igual en cualquier camión. Una **VM** es una **casa prefabricada entera**: más aislada, pero mucho más pesada de mover. **Kubernetes** es la **empresa de logística** que gestiona miles de cajas en un almacén. **AWS** es el **terreno que alquilas** para poner las cajas o las casas.

En esta práctica, tu aplicación Spring se ejecuta desde el IDE como siempre, y solo la base de datos va en Docker.

P.2.2 Conceptos básicos de Docker

  • Imagen: la plantilla de solo lectura con el programa ya instalado y configurado. Las oficiales se descargan de Docker Hub (postgres, mongo, mysql...). La etiqueta tras los dos puntos indica la versión: postgres:17.
  • Contenedor: una instancia en ejecución de una imagen. De una misma imagen puedes arrancar varios contenedores independientes.
  • Mapeo de puertos: el contenedor está aislado, así que para hablar con él desde tu ordenador se "conecta" un puerto tuyo con uno suyo: "5432:5432" significa puerto de tu PC : puerto del contenedor.
  • Volumen: una zona de almacenamiento fuera del contenedor donde se guardan los datos. Si borras el contenedor, los datos del volumen sobreviven; sin volumen, se perderían.
  • Docker Compose: permite describir uno o varios contenedores en un fichero docker-compose.yml y arrancarlos todos con un comando. Es "la base de datos como código": cualquiera que clone tu proyecto la levanta exactamente igual.

Analogía para quien programa en Java Una **imagen** es como una **clase** y un **contenedor**, como un **objeto**: la imagen es el molde y cada contenedor es una instancia concreta creada a partir de él, con su propio estado.

P.2.3 PostgreSQL con Docker Compose

Primero instala Docker: Docker Desktop en Windows o Mac, o Docker Engine con el plugin de Compose en Linux. Comprueba que funciona con docker --version y docker compose version.

Después crea un fichero docker-compose.yml en la raíz del proyecto (junto a build.gradle):

yaml

services:
  postgres:
    image: postgres:17                # imagen oficial de PostgreSQL, versión 17
    container_name: miapp-db          # nombre del contenedor
    environment:
      POSTGRES_DB: miapp              # crea esta base de datos automáticamente
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: postgres
    ports:
      - "5432:5432"                   # puerto_de_tu_PC:puerto_del_contenedor
    volumes:
      - pgdata:/var/lib/postgresql/data   # los datos se guardan en el volumen

volumes:
  pgdata:                             # declara el volumen con nombre

Gracias a POSTGRES_DB, la base de datos ya existe al arrancar, así que no hace falta ningún CREATE DATABASE. Las tablas las creará Hibernate a partir de tus entidades (P.4.6).

Si usas `postgres:18` o posterior, la imagen cambió dónde guarda los datos: monta el volumen en `/var/lib/postgresql` en lugar de `/var/lib/postgresql/data`.

P.2.4 Comandos básicos

Se ejecutan en una terminal, desde la carpeta del proyecto (donde está el docker-compose.yml):

Comando Qué hace
docker compose up -d Arranca los contenedores en segundo plano (-d). La primera vez descarga la imagen
docker compose ps Muestra qué contenedores están en marcha
docker compose logs -f Muestra los logs en directo (útil si algo falla)
docker compose down Para y elimina los contenedores; los datos del volumen se conservan
docker compose down -v Lo mismo, pero borrando también los volúmenes: empezar de cero

P.2.5 Conectar Spring y revisar la base de datos

Spring no sabe ni le importa que PostgreSQL esté en Docker: gracias al mapeo de puertos, para él es una base de datos más en localhost:5432. Basta con que los datos de conexión de application.properties (P.4.6) coincidan con los del docker-compose.yml: nombre de la base de datos, usuario y contraseña.

Para ver las tablas y los datos puedes conectarte con pgAdmin, DBeaver o el panel Database de IntelliJ (host localhost, puerto 5432, usuario y contraseña postgres), o entrar por consola dentro del contenedor:

bash

docker exec -it miapp-db psql -U postgres -d miapp

Dentro, \dt lista las tablas, \d pedidos muestra la estructura de una tabla y \q sale.

Opcional: que Spring arranque Docker por ti. Con la dependencia Docker Compose Support (P.1.6), Spring Boot detecta el docker-compose.yml, levanta el contenedor al arrancar la aplicación y configura la conexión automáticamente. Es cómodo, pero conviene hacerlo primero a mano para entender qué está pasando.

Más adelante también se puede meter la propia aplicación Spring en un contenedor (con un fichero Dockerfile) y levantar aplicación y base de datos juntas con Compose. Es lo que se hace para desplegar; para desarrollar la práctica no hace falta.

P.2.6 Problemas típicos

  • Connection refused al arrancar Spring: el contenedor no está en marcha. Compruébalo con docker compose ps y arráncalo con docker compose up -d.
  • El puerto 5432 ya está ocupado: tienes PostgreSQL instalado también en tu ordenador. Cambia el mapeo a "5433:5432" y la URL de conexión a localhost:5433.
  • Los datos desaparecen: falta la sección volumes, o has ejecutado docker compose down -v.
  • Los datos no desaparecen y quieres empezar de cero: docker compose down -v y vuelve a arrancar.

P.3 Crear servicios REST con Spring

Lo primero es tener la dependencia Spring Web en el proyecto: trae todo lo necesario para aplicaciones web y servicios RESTful.

P.3.1 El controlador

Un controlador es la clase que recibe las peticiones HTTP y devuelve las respuestas. Antes se marcaba con @Controller (es un componente que atiende peticiones) más @ResponseBody (lo que devuelven los métodos es el cuerpo de la respuesta, en JSON o XML). Hoy se usa @RestController, que combina las dos y es la preferida para APIs REST. Con @RequestMapping a nivel de clase se fija la ruta base de todos sus endpoints:

java

@RestController
@RequestMapping("/api/libros")   // todos los endpoints empiezan por /api/libros
public class LibroController {
    // aquí van los endpoints
}

P.3.2 Un método por endpoint

Cada método del controlador es un endpoint. @RequestMapping a nivel de método permite indicar ruta y verbo, pero es más claro usar las anotaciones especializadas, una por verbo HTTP:

Anotación Verbo
@GetMapping GET (obtener)
@PostMapping POST (crear)
@PutMapping PUT (sustituir)
@PatchMapping PATCH (modificar parcialmente)
@DeleteMapping DELETE (eliminar)

java

@RestController
@RequestMapping("/api/v1/libros")
public class LibroController {

    @GetMapping                       // GET /api/v1/libros
    public List<Libro> getAllLibros() { ... }

    @GetMapping("/{id}")              // GET /api/v1/libros/7
    public Libro getLibroById(@PathVariable Long id) { ... }

    @PostMapping                      // POST /api/v1/libros
    public ResponseEntity<Libro> createLibro(@RequestBody Libro nuevoLibro) { ... }
}

P.3.3 Recoger datos de la petición

Hay tres anotaciones para sacar datos de la petición, y cada una corresponde a una parte de la URL o del mensaje que vimos en el tema 3:

Anotación De dónde saca el dato Ejemplo
@PathVariable De una variable del path (identifica un recurso) /libros/{id} → id
@RequestParam De un parámetro de la query (filtros); puede ser opcional u obligatorio y tener valor por defecto /libros?autor=J.K. Rowling → autor
@RequestBody Del cuerpo de la petición, convertido a un objeto Java. Imprescindible en POST y PUT { "titulo": "..." } → Libro

P.3.4 Controlar la respuesta con ResponseEntity

Si el método devuelve un objeto, Spring lo convierte a JSON y responde 200 OK. Para elegir el código de estado (201 Created, 404 Not Found...) y añadir cabeceras, se devuelve un ResponseEntity, que envuelve cuerpo, código y cabeceras:

java

@PostMapping
public ResponseEntity<Libro> createLibro(@RequestBody Libro nuevoLibro) {
    Libro libroGuardado = libroService.save(nuevoLibro);
    return new ResponseEntity<>(libroGuardado, HttpStatus.CREATED);   // 201
}

P.4 JPA y bases de datos relacionales

P.4.1 El problema y la solución (ORM)

En Java trabajamos con objetos (con herencia, referencias entre ellos...), pero una base de datos relacional guarda tablas con filas, columnas y claves foráneas. Tradicionalmente se usaba JDBC, que obliga a escribir mucho código repetitivo, abrir y cerrar conexiones a mano y copiar a mano cada columna del resultado a los atributos del objeto: propenso a errores y difícil de mantener.

Las herramientas ORM (Object-Relational Mapping) automatizan esa conversión en los dos sentidos entre filas de la base de datos y objetos en memoria.

P.4.2 JPA, Hibernate y Spring Data JPA

JPA (Jakarta Persistence API) no es una librería que se ejecute, sino una especificación: define interfaces, convenciones y anotaciones comunes para la persistencia. Como el código se programa contra JPA, se puede cambiar la implementación sin reescribir la lógica. La implementación más usada es Hibernate. Spring Data JPA añade una capa más por encima, que configura todo y genera automáticamente el acceso a datos mediante repositorios.

Analogía: el enchufe **JPA** es el estándar del enchufe (la forma que tiene); **Hibernate** es un aparato concreto que encaja en ese enchufe; **Spring Data JPA** es una regleta que te lo deja todo conectado para que solo tengas que enchufar.

Sus conceptos centrales son las entidades (@Entity: una clase Java que se mapea a una tabla) y el mapeo de relaciones, que convierte claves foráneas en referencias entre objetos.

Qué hace exactamente cada pieza

JPA: el contrato. Si miras dentro de la librería de JPA, casi todo son interfaces y anotaciones sin código que haga nada. Define cuatro cosas:

  • Las anotaciones con las que describes cómo se guarda un objeto: @Entity, @Id, @Column, @ManyToOne...
  • La interfaz EntityManager, con las operaciones básicas: persist (guardar), find (buscar por id), merge (actualizar), remove (borrar) y createQuery (consultar).
  • JPQL, un lenguaje de consultas parecido a SQL pero que trabaja con clases y atributos en lugar de tablas y columnas: SELECT u FROM Usuario u WHERE u.email = :email.
  • Las reglas de comportamiento: cuándo un objeto está "vigilado", qué pasa al terminar una transacción, qué significan LAZY y EAGER...

Es como el reglamento del fútbol: dice cómo se juega, pero no juega.

Hibernate: el que hace el trabajo. Implementa ese contrato. Concretamente:

  1. Lee tus entidades al arrancar y construye un mapa interno: "la clase Usuario va a la tabla usuarios, el campo nome a la columna nome, pedidos se resuelve con la FK usuario_id de la tabla pedidos".
  2. Crea o actualiza las tablas a partir de ese mapa, si se lo pides con ddl-auto (P.4.6): genera los CREATE TABLE, ALTER TABLE y las claves foráneas.
  3. Traduce tus operaciones con objetos a SQL: save(usuario) se convierte en un INSERT; findById(5), en un SELECT cuya fila se convierte en un objeto Usuario relleno.
  4. Traduce JPQL al SQL de tu base de datos. Cada base de datos tiene pequeñas diferencias de sintaxis, y Hibernate las conoce mediante dialectos; por eso puedes cambiar de PostgreSQL a MySQL sin reescribir las consultas.
  5. Vigila los objetos que cargas (el contexto de persistencia). Dentro de un @Transactional, si haces usuario.setNome("Ana"), Hibernate detecta el cambio y genera el UPDATE al final sin que llames a save. Es el dirty checking que se ve en rexistrarPedido (P.4.8).
  6. Gestiona la carga LAZY: en lugar del objeto relacionado pone un "sustituto" (proxy) y solo lanza el SELECT cuando accedes a él.

Hibernate tampoco habla directamente con PostgreSQL: le pasa el SQL al driver JDBC (la dependencia org.postgresql:postgresql), que es quien lo envía a la base de datos.

Spring Data JPA: los repositorios. Escribe por ti la implementación de los repositorios. Tú solo declaras una interfaz (P.4.8) y, cuando llamas a usuarioRepository.findByEmail(...), por dentro está usando el EntityManager de JPA, es decir, Hibernate.

Spring Boot: el que lo conecta todo. Crea la conexión a la base de datos con los datos de application.properties, arranca Hibernate y, además, ejecuta los scripts schema.sql y data.sql si existen (P.4.7). Estos scripts los ejecuta Spring Boot directamente con JDBC, no Hibernate.

Así, cuando haces usuarioRepository.save(usuario), la llamada recorre esta cadena:

Spring Data JPA (tu repositorio) → JPA (EntityManager.persist) → Hibernate (genera el INSERT) → driver JDBC → PostgreSQL (en su contenedor Docker, P.2)

En la práctica, tú escribes anotaciones de JPA en tus clases y declaras interfaces de Spring Data JPA; Hibernate trabaja por debajo sin que lo veas. Con el starter spring-boot-starter-data-jpa vienen los tres incluidos.

P.4.3 Del modelo E/R a las entidades

El diseño de la base de datos se hace igual que siempre; lo que cambia es el último paso:

  1. Diseña el modelo entidad-relación. Es lo más importante y no cambia.
  2. Pásalo a modelo relacional (aunque sea en papel) para tener claro dónde va cada clave foránea y qué tablas intermedias hay.
  3. En lugar de escribir el script CREATE TABLE, escribe las clases @Entity. Hibernate generará las tablas por ti (P.4.6).
  4. Carga los datos con un data.sql, desde Java o a través de la propia API (P.4.7).

La traducción del modelo a JPA es casi directa:

En tu modelo En Java (JPA)
Entidad / tabla Clase con @Entity y @Table(name = "...")
Atributo / columna Campo, con @Column(nullable = false, unique = true, length = ...) si hace falta
Clave primaria @Id + @GeneratedValue(strategy = Generationype.IDENTITY)
Relación 1:N (FK en el lado N) En la clase del lado N: @ManyToOne(fetch = FetchType.LAZY) + @JoinColumn(name = "x_id"). En el lado 1, si quieres navegar al revés: @OneToMany(mappedBy = "...")
Relación 1:1 @OneToOne + @JoinColumn(unique =true) en el lado que lleva la FK
Relación N:M sin atributos @ManyToMany + @JoinTable
Relación N:M con atributos (p. ej., una matrícula con nota) No uses @ManyToMany: crea una entidad intermedia propia (Matricula) con dos @ManyToOne y sus atributos (nota, data...)

Las anotaciones de relación se detallan en el apartado siguiente.

P.4.4 Relaciones entre entidades

Anotación Relación Claves
@ManyToOne Muchos a uno; la más habitual. Es el lado propietario: la tabla que tiene la clave foránea Se configura con @JoinColumn(name = "fk_id"). Por defecto es EAGER: hay que cambiarla a FetchType.LAZY
@OneToMany Uno a muchos: la colección inversa; no tiene la clave foránea Usa mappedBy con el nombre del atributo del lado propietario: @OneToMany(mappedBy = "usuario"). Por defecto es LAZY. Admite cascade (propagar guardar/borrar) y orphanRemoval = true (borrar los hijos que se quitan de la colección)
@OneToOne Uno a uno (p. ej., Usuario y Perfil) El propietario lleva @JoinColumn(name = "perfil_id", unique = true); el inverso, mappedBy
@ManyToMany Muchos a muchos sin atributos propios, con tabla intermedia Se define con @JoinTable; el lado inverso usa mappedBy = "roles"

java

@ManyToMany
@JoinTable(
    name = "usuarios_roles",
    joinColumns = @JoinColumn(name = "usuario_id"),
    inverseJoinColumns = @JoinColumn(name = "rol_id")
)
private Set<Rol> roles = new HashSet<>();

EAGER significa que al cargar el objeto se carga también el relacionado, aunque no lo uses; LAZY, que se carga solo cuando lo pides. Por eso conviene poner LAZY en los ...ToOne.

P.4.5 Ejemplo: usuarios y pedidos

Relación 1:N (un usuario tiene muchos pedidos). En el modelo relacional, la clave foránea va siempre en el lado "muchos" (la tabla pedidos), que en JPA es el lado propietario; Usuario es el lado inverso:

java

@Entity
@Table(name = "usuarios")
public class Usuario {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)   // id autoincremental
    private Long id;

    @Column(nullable = false, length = 100)
    private String nome;

    @Column(nullable = false, unique = true)
    private String email;

    @OneToMany(mappedBy = "usuario", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<Pedido> pedidos = new ArrayList<>();

    public void addPedido(Pedido pedido) {   // mantiene los dos lados sincronizados
        pedidos.add(pedido);
        pedido.setUsuario(this);
    }
    // constructores, getters y setters...
}

@Entity
@Table(name = "pedidos")
public class Pedido {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 20)
    private String codigo;

    private LocalDate dataPedido;                  // en la tabla será la columna data_pedido

    @ManyToOne(fetch = FetchType.LAZY)             // LAZY: no carga el usuario si no hace falta
    @JoinColumn(name = "usuario_id", nullable = false)
    private Usuario usuario;
    // constructores, getters y setters...
}

P.4.6 Conexión y creación automática de las tablas

Se añaden el starter y el driver de la base de datos (por ejemplo, PostgreSQL) en build.gradle (P.1.6):

gradle

dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-data-jpa'
    runtimeOnly 'org.postgresql:postgresql'
}

Y la conexión se configura en src/main/resources/application.properties. Los datos deben coincidir con los del docker-compose.yml (P.2.3):

properties

spring.datasource.url=jdbc:postgresql://localhost:5432/miapp
spring.datasource.username=postgres
spring.datasource.password=postgres

spring.jpa.hibernate.ddl-auto=update   # Hibernate crea/actualiza las tablas a partir de las entidades
spring.jpa.show-sql=true               # muestra en consola el SQL generado (muy útil para aprender)

No se escribe ningún CREATE TABLE. Con la propiedad ddl-auto, Hibernate genera las tablas al arrancar a partir de las entidades. Para el Pedido de P.4.5 genera algo así (lo verás en la consola gracias a show-sql):

sql

create table pedidos (
    id bigint generated by default as identity,
    codigo varchar(20) not null,
    data_pedido date,
    usuario_id bigint not null,
    primary key (id)
);
alter table pedidos add constraint FK... foreign key (usuario_id) references usuarios;

Fíjate en que dataPedido se convierte en data_pedido: Spring Boot pasa automáticamente los nombres de camelCase a snake_case. Importa a la hora de escribir SQL a mano (P.4.7).

Valor de ddl-auto Qué hace al arrancar Cuándo usarlo
create Borra y recrea todas las tablas (vacías) Desarrollo con datos de prueba en data.sql
create-drop Como create, y además las borra al parar la app Tests
update Crea lo que falte sin borrar datos Desarrollo, cuando quieres conservar los datos
validate No toca nada; solo comprueba que las tablas coinciden con las entidades Producción
none No hace nada: las tablas las creas tú Cuando el esquema se gestiona aparte

En un proyecto real en producción se usa `validate` y el esquema se gestiona con **scripts SQL versionados** mediante herramientas como **Flyway** o **Liquibase**. Para una práctica, `create` o `update` es lo normal.

Hibernate crea las tablas, pero no la base de datos. Con el docker-compose.yml de P.2.3 no hay problema, porque POSTGRES_DB ya la crea; con un PostgreSQL instalado a mano habría que hacer antes CREATE DATABASE miapp;.

Qué pasa al arrancar la aplicación

  1. Spring Boot lee application.properties y abre la conexión con PostgreSQL mediante el driver JDBC.
  2. Hibernate lee las clases @Entity y, según ddl-auto, crea o actualiza las tablas.
  3. Spring Boot ejecuta data.sql, si existe y está activado (P.4.7).
  4. Spring Data JPA genera las implementaciones de los repositorios.
  5. La aplicación queda lista: cada llamada a un repositorio pasa por Hibernate, que genera el SQL y lo envía por el driver.

P.4.7 Cargar datos iniciales

Las tablas se crean vacías. Para meter datos hay tres caminos, y ninguno es obligatorio:

Opción Cómo Ventajas e inconvenientes
Por la API Peticiones POST desde Postman o curl No hace falta script y de paso pruebas la API; pero con ddl-auto=create hay que repetirlo en cada arranque
data.sql Un fichero con INSERT que Spring Boot ejecuta al arrancar Lo más cómodo para tener siempre los mismos datos de prueba
CommandLineRunner Una clase Java que crea objetos y los guarda con los repositorios al arrancar Útil si prefieres trabajar con objetos en lugar de SQL

Con data.sql, el fichero va en src/main/resources/data.sql:

sql

INSERT INTO usuarios (nome, email) VALUES ('Ana', 'ana@exemplo.com');
INSERT INTO usuarios (nome, email) VALUES ('Brais', 'brais@exemplo.com');

INSERT INTO pedidos (codigo, data_pedido, usuario_id) VALUES ('P-001', '2026-09-15', 1);
INSERT INTO pedidos (codigo, data_pedido, usuario_id) VALUES ('P-002', '2026-09-20', 1);

Y en application.properties:

properties

spring.jpa.hibernate.ddl-auto=create
spring.jpa.defer-datasource-initialization=true   # ejecutar data.sql DESPUÉS de que Hibernate cree las tablas
spring.sql.init.mode=always                       # ejecutar los scripts también con bases de datos no embebidas

defer-datasource-initialization es necesaria porque, por defecto, Spring Boot ejecuta data.sql antes de que Hibernate cree las tablas, y los INSERT fallarían porque las tablas aún no existen.

Tres detalles para evitar errores:

  1. Usa create, no update, junto con data.sql. Con create las tablas se recrean vacías en cada arranque y el script las rellena siempre igual. Con update los datos se conservan y los INSERT se repetirían en cada arranque, duplicando filas o fallando por las restricciones unique.
  2. Usa los nombres reales de tabla y columna, en snake_case (data_pedido, usuario_id), no los de los atributos Java.
  3. No escribas los id a mano: deja que los genere PostgreSQL. Si los pones tú, su contador interno no se entera y el siguiente POST desde la API intentará usar el id 1, que ya existe, con un error de clave duplicada. Como los INSERT van en orden, sabes que Ana será el 1 y Brais el 2, y puedes usar esos números en las claves foráneas.

Curiosidad: `import.sql` Hibernate tiene su propio mecanismo: si hay un fichero `import.sql` en `src/main/resources` y `ddl-auto` es `create` o `create-drop`, lo ejecuta justo después de crear las tablas. Funciona, pero en Spring Boot lo habitual es `data.sql`.

P.4.8 Repositorios y servicios

Con JpaRepository no hace falta escribir SQL para el CRUD básico ni implementar la interfaz: basta con declararla. Además, Spring deduce la consulta del nombre del método (derived query), y para casos complejos se escribe JPQL con @Query:

java

@Repository
public interface UsuarioRepository extends JpaRepository<Usuario, Long> {
    Optional<Usuario> findByEmail(String email);          // SQL deducido del nombre

    @Query("SELECT u FROM Usuario u WHERE u.email LIKE %:dominio")
    List<Usuario> buscarPorDominioEmail(@Param("dominio") String dominio);
}

En los apuntes el primer ejemplo pone `extends JpaRepository` sin tipos; lo correcto es `JpaRepository<Usuario, Long>` (entidad y tipo de su id), como aparece en el ejemplo posterior.

En el servicio, las operaciones se agrupan en transacciones con @Transactional: al terminar el método con éxito, JPA sincroniza automáticamente con la base de datos los cambios hechos en los objetos (el flush), sin llamar a save:

java

@Service
public class UsuarioService {
    private final UsuarioRepository usuarioRepository;

    public UsuarioService(UsuarioRepository usuarioRepository) {   // inyección por constructor
        this.usuarioRepository = usuarioRepository;
    }

    @Transactional
    public void rexistrarPedido(Long usuarioId, String codigoPedido) {
        // 1. Obtener la entidad (pasa a estado "Managed": JPA vigila sus cambios)
        Usuario usuario = usuarioRepository.findById(usuarioId)
                .orElseThrow(() -> new IllegalArgumentException("Usuario non atopado"));
        // 2. Modificar los objetos en memoria
        Pedido novoPedido = new Pedido();
        novoPedido.setCodigo(codigoPedido);
        usuario.addPedido(novoPedido);
        // 3. Al acabar el método, se hace el flush y se guardan los cambios
    }
}

P.4.9 Rendimiento y buenas prácticas

  • Estrategia de carga: las relaciones ...ToOne son EAGER por defecto y lanzan consultas inmediatas; hay que ponerlas en FetchType.LAZY.
  • Problema N+1: al recorrer una lista de N entidades con relaciones LAZY, Hibernate puede lanzar 1 consulta para la lista y N consultas más, una por cada hijo. Se evita con JOIN FETCH en JPQL o con @EntityGraph, que convierte todo en una única consulta con LEFT OUTER JOIN.
  • Serialización a JSON: las relaciones bidireccionales (usuario → pedido → usuario → ...) provocan StackOverflowError cuando Jackson las convierte a JSON, porque entra en bucle. La mejor práctica es no exponer las entidades en la API y devolver DTOs (objetos pensados solo para la respuesta).

java

@Repository
public interface UsuarioRepository extends JpaRepository<Usuario, Long> {
    @EntityGraph(attributePaths = {"pedidos"})   // carga los pedidos en un único JOIN
    List<Usuario> findAll();

    @EntityGraph(attributePaths = {"pedidos"})
    Optional<Usuario> findByEmail(String email);
}

Analogía: el problema N+1 Es como hacer la compra yendo al súper una vez para ver qué hay y luego **una vez más por cada producto**. `@EntityGraph` o `JOIN FETCH` es hacer **un solo viaje** con toda la lista.

P.5 Consultas avanzadas: filtros dinámicos

Es habitual que un endpoint deba filtrar por varios criterios que el usuario puede enviar o no (GET /users?email=...&name=...). En lugar de crear un método por cada combinación posible, Spring Data ofrece dos soluciones.

P.5.1 Query By Example

Se busca usando un objeto de ejemplo: Spring mira los campos que no son null y construye la consulta con ellos, ignorando el resto. Se envuelve el objeto en un Example; por defecto la coincidencia es exacta:

java

User userFilter = new User();
userFilter.setEmail(email);
userFilter.setName(name);
Example<User> filter = Example.of(userFilter);
List<User> result = users.findAll(filter);   // users es el UserRepository

Con ExampleMatcher se personaliza la búsqueda, por ejemplo para buscar coincidencias parciales e ignorar mayúsculas, en todos los campos o solo en algunos:

java

ExampleMatcher matcher = ExampleMatcher.matching()
    .withIgnoreCase()                                              // sin distinguir mayúsculas
    .withStringMatcher(ExampleMatcher.StringMatcher.CONTAINING);   // "contiene" en vez de "igual"
Example<User> filter = Example.of(userFilter, matcher);

// Reglas por campo:
ExampleMatcher matcher2 = ExampleMatcher.matching()
    .withIgnorePaths("name")      // no aplicar reglas al campo name
    .withIgnoreCase("email");     // ignorar mayúsculas solo en email

Así basta un único findAll para todas las combinaciones de filtros. Sirve para el 90% de los casos.

P.5.2 Criteria y Query

Para consultas que Query By Example no cubre (condiciones OR, rangos de fechas, negaciones), hay un enfoque programático con las clases Criteria y Query y un MongoTemplate inyectado (este ejemplo es para MongoDB). Requiere más código, pero da control total:

java

public List<User> findUsersByCriteria(String email, Integer age) {
    Criteria criteria = new Criteria();
    if (email != null && !email.isEmpty()) {
        criteria.and("email").regex(".*" + email + ".*", "i");   // parcial, sin mayúsculas
    }
    if (age != null) {
        criteria.and("age").is(age);
    }
    Query query = Query.query(criteria);
    return mongoTemplate.find(query, User.class);
}

P.6 Paginación

Devolver todos los resultados de golpe es ineficiente para servidor y cliente. La paginación divide los resultados en páginas pequeñas, lo que mejora el rendimiento, el consumo de memoria y el tiempo de respuesta.

P.6.1 Paginación tradicional: Pageable y Page

La interfaz Pageable describe qué página, de qué tamaño y con qué orden. Si un método del repositorio la recibe, la consulta se pagina sola, y devuelve un Page<T> con los elementos de esa página y metadatos: total de páginas (getTotalPages()), total de elementos (getTotalElements()) y si es la primera o la última (isFirst(), isLast()):

java

Pageable pageable = PageRequest.of(page, size, Sort.by("nome").ascending());
Page<Libro> libros = libroRepository.findAll(pageable);

Tiene dos desventajas: para saber el total, la base de datos hace un segundo recuento completo, lento con muchos datos; y si los datos cambian entre peticiones, las páginas siguientes pueden salir inconsistentes (elementos repetidos o saltados).

P.6.2 Paginación con cursores

En lugar de un número de página (offset), se usa un cursor: un "marcador" del último elemento recibido. El cliente envía ese cursor y el servidor devuelve los siguientes a partir de él. Es más eficiente y escalable porque no necesita contar el total, resiste cambios en los datos y sirve para flujos infinitos. Su pega: no se puede saltar a una página concreta (la 100), solo avanzar o retroceder.

Analogía: el marcapáginas La paginación tradicional es decir "ábreme el libro por la página 57": si alguien ha arrancado hojas, caes en otro sitio. El cursor es un **marcapáginas**: sigues justo donde lo dejaste, aunque el libro haya cambiado, pero no puedes saltar a la página 57 sin pasar por las anteriores.

Spring Data no trae una abstracción para cursores, pero se implementa en tres pasos: elegir un campo único y ordenable como cursor (la fecha de creación createdAt o un ObjectId de MongoDB, que ya incluye un timestamp); hacer que el repositorio filtre los elementos posteriores al cursor, y devolver el cursor del último elemento en la respuesta:

java

@GetMapping("/libros")
public List<Libro> getLibros(@RequestParam(required = false) Long lastCreatedAt,
                             @RequestParam(defaultValue = "20") int limit) {
    if (lastCreatedAt == null) return libroRepository.findFirstLibros(limit);
    else return libroRepository.findNextLibros(lastCreatedAt, limit);
}

public interface LibroRepository extends MongoRepository<Libro, String> {
    List<Libro> findFirstLibros(int limit);                 // primera página
    @Query("{ 'createdAt' : { $lt: ?0 } }")                 // los anteriores al cursor
    List<Libro> findNextLibros(Long createdAt, int limit);  // páginas siguientes
}

json

{ "data": [ /* ... 20 libros ... */ ], "nextCursor": 1678888400000 }

El cliente usa nextCursor como lastCreatedAt en la siguiente llamada.

Es un ejemplo simplificado de los apuntes. Fíjate en que la respuesta usa un envoltorio `data`, algo que el tema 3 desaconseja en general; aquí se justifica porque hay que devolver el cursor junto a la lista.

P.7 PATCH y JSON Patch en Spring

Con PUT hay que enviar el recurso completo, lo que es poco eficiente para cambiar un solo campo. Por eso en 2010 se introdujo PATCH, para actualizaciones parciales: su cuerpo es un conjunto de instrucciones de cambio. Para estandarizarlas existe JSON Patch (RFC 6902): un array de operaciones con op (add, replace, remove, test, copy, move), path (el campo) y value (el nuevo valor, si hace falta), enviado con Content-Type: application/json-patch+json.

json

[
  { "op": "replace", "path": "/nombre", "value": "Novo Nome" },
  { "op": "replace", "path": "/email",  "value": "novo.email@exemplo.com" }
]

En Java se usa la librería java-json-tools:json-patch:

gradle

implementation 'com.github.java-json-tools:json-patch:1.13'

El proceso para aplicar un PATCH tiene cinco pasos: obtener el objeto de la base de datos, convertirlo a JSON (JsonNode) con Jackson, aplicar el parche con la librería, convertir el JSON de vuelta a objeto y guardarlo:

java

Usuario usuarioExistente = usuarioRepository.findById(id).orElseThrow(...);        // 1
JsonNode jsonUsuario = mapper.convertValue(usuarioExistente, JsonNode.class);        // 2
JsonNode jsonUsuarioActualizado = operations.apply(jsonUsuario);                     // 3
Usuario usuarioActualizado = mapper.convertValue(jsonUsuarioActualizado, Usuario.class); // 4
usuarioRepository.save(usuarioActualizado);                                          // 5

Spring puede recibir directamente un JsonPatch, pero si quieres revisar las operaciones antes de aplicarlas (por ejemplo, que solo toquen ciertos campos, como en el ejercicio de "ProXecto Áxil" del tema 3), es mejor recibir el cuerpo como List<Map<String, Object>> y convertirlo después. Conviene encapsularlo en una clase reutilizable:

java

@Service
public class PatchUtils {
    private final ObjectMapper mapper;
    public PatchUtils(ObjectMapper mapper) { this.mapper = mapper; }

    @SuppressWarnings("unchecked")
    public <T> T applyPatch(T data, List<Map<String, Object>> updates) throws JsonPatchException {
        JsonPatch operations = mapper.convertValue(updates, JsonPatch.class);   // 1. a JsonPatch
        JsonNode json = mapper.convertValue(data, JsonNode.class);              // 2. objeto a JSON
        JsonNode updatedJson = operations.apply(json);                          // 3. aplicar
        return (T) mapper.convertValue(updatedJson, data.getClass());           // 4. de vuelta a objeto
    }
}

Para entenderlo mejor [RFC 6902: JSON Patch](https://www.rfc-editor.org/rfc/rfc6902.html) — el estándar con todas las operaciones y ejemplos (documento, inglés).

P.8 Serialización con Jackson

Serializar es convertir un objeto Java a JSON; deserializar, lo contrario. Spring usa por defecto la librería Jackson, que se controla con anotaciones en las clases.

P.8.1 Ocultar y renombrar campos

Anotación Efecto Uso típico
@JsonInclude(JsonInclude.Include.NON_NULL) Omite los campos que valen null Reducir el tamaño de las respuestas, ocultar campos no relevantes, no exponer datos sensibles cuando no están
@JsonIgnore Ignora el campo siempre, al serializar y al deserializar Contraseñas, tokens
@JsonProperty("nombre") Cambia el nombre del campo en el JSON Adaptarse a las convenciones de la API
@JsonFormat(pattern = "dd-MM-yyyy") Da formato a fechas y horas yyyy-MM-dd HH:mm:ss

java

@JsonInclude(JsonInclude.Include.NON_NULL)
public class Usuario {
    private String email;
    @JsonIgnore                        // nunca sale en el JSON
    private String contrasinal;
    @JsonProperty("nomeCompleto")      // en el JSON se llama "nomeCompleto"
    private String nome;
    @JsonFormat(pattern = "dd-MM-yyyy")
    private Date dataRexistro;
}

Por ejemplo, un Libro con isbn = null y @JsonInclude(NON_NULL) se serializa sin el campo isbn:

json

{ "id": 123, "titulo": "A viaxe do elefante", "autor": "José Saramago", "paginas": 215 }

P.8.2 Vistas con @JsonView

A veces la misma clase debe mostrarse de forma distinta según el endpoint: en una lista solo lo básico (id, nombre) y en el detalle todo (email, fecha de registro). @JsonView crea "vistas" sin tener que crear varias clases:

java

public class User {
    public interface UserSummaryView {}                            // 1. marcadores de vista
    public interface UserDetailView extends UserSummaryView {}    //    el detalle incluye el resumen

    @JsonView(UserSummaryView.class) private Long id;              // 2. cada campo, en su vista
    @JsonView(UserSummaryView.class) private String name;
    @JsonView(UserSummaryView.class) private String country;
    @JsonView(UserDetailView.class)  private String email;
    @JsonView(UserDetailView.class)  private Date registrationDate;
}

@RestController
public class UserController {
    @GetMapping("/users")
    @JsonView(User.UserSummaryView.class)       // 3. la lista solo muestra id, name, country
    public List<User> listUsers() { ... }

    @GetMapping("/users/{id}")
    @JsonView(User.UserDetailView.class)        //    el detalle lo muestra todo
    public User getUser(@PathVariable Long id) { ... }
}

Como UserDetailView hereda de UserSummaryView, la vista de detalle incluye también los campos del resumen. Los campos sin @JsonView no aparecen en ninguna vista. Sus ventajas: simplicidad (evita crear varios DTOs), flexibilidad (controlas lo que se expone sin tocar la lógica) y mantenimiento (los cambios se hacen en un solo sitio).

P.9 Validación con Hibernate Validator

Hay que comprobar que los datos que llegan son válidos antes de procesarlos. Hacerlo con muchos if/else da "código espagueti". La especificación Bean Validation (JSR-380) permite declarar las reglas con anotaciones en los atributos; su implementación más popular es Hibernate Validator. Se añade con:

gradle

implementation 'org.springframework.boot:spring-boot-starter-validation'
Anotación Regla
@NotNull No puede ser null
@NotEmpty Ni null ni vacío (Strings, colecciones, arrays)
@NotBlank String ni null, ni vacío, ni solo espacios
@Size(min=x, max=y) Tamaño entre min y max
@Min(x) / @Max(x) Número ≥ x / ≤ x
@Email Formato de email válido
@Pattern(regexp="...") Cumple una expresión regular
@Valid Valida también los objetos anidados

Cada anotación admite un mensaje propio con message:

java

@Document(collection = "users")
@JsonInclude(JsonInclude.Include.NON_NULL)
public class User {
    @Id
    @NotBlank(message = "O campo 'email' non pode estar baleiro")
    @Email(message = "O formato do email non é válido")
    private String email;

    @Size(min = 2, max = 50, message = "O nome debe ter entre 2 e 50 caracteres")
    private String name;

    @Valid                       // valida también cada User de la lista
    private List<User> friends;
}

Para que Spring active la validación en un endpoint, se pone @Valid delante del parámetro @RequestBody. Si los datos no cumplen las reglas, Spring lanza MethodArgumentNotValidException antes de ejecutar el método, y por defecto responde 400 Bad Request. Para devolver un error más detallado se captura la excepción con un ExceptionHandler (siguiente apartado).

java

@PostMapping
public ResponseEntity<User> createUser(@RequestBody @Valid User user) {
    // si 'user' no es válido, nunca se llega aquí
}

P.10 Gestión centralizada de errores

Si no se hace nada, cualquier excepción no capturada produce la respuesta de error por defecto de Spring, que no suele tener el formato JSON deseado ni información útil. Lo recomendado es centralizar el manejo con @RestControllerAdvice y @ExceptionHandler.

@RestControllerAdvice marca una clase que intercepta las excepciones de todos los controladores (combina @ControllerAdvice y @ResponseBody, así que lo que devuelve se convierte en JSON). Dentro, cada método con @ExceptionHandler(TipoDeExcepcion.class) se ejecuta cuando se lanza esa excepción, la recibe como parámetro y devuelve un ResponseEntity con el código y el cuerpo que queramos:

java

@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(NoSuchElementException.class)             // recurso no encontrado → 404
    public ResponseEntity<String> handleNoSuchElement(NoSuchElementException ex) {
        return new ResponseEntity<>("Recurso non atopado: " + ex.getMessage(), HttpStatus.NOT_FOUND);
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)    // validación fallida → 400 + detalle
    public ResponseEntity<Map<String, String>> handleValidation(MethodArgumentNotValidException ex) {
        Map<String, String> errors = new HashMap<>();
        ex.getBindingResult().getFieldErrors().forEach(error ->
            errors.put(error.getField(), error.getDefaultMessage()));
        return new ResponseEntity<>(errors, HttpStatus.BAD_REQUEST);
    }
}

Analogía: el departamento de reclamaciones En vez de que cada ventanilla (controlador) gestione sus propias quejas como pueda, todas las envían a **un único departamento de reclamaciones** (`@RestControllerAdvice`), que responde siempre con el mismo formato.

Otras estrategias:

Excepciones personalizadas. Es buena práctica crear tus propias excepciones con significado (RecursoNonAtopadoException) en lugar de genéricas como RuntimeException, y capturarlas en el handler global. Con @ResponseStatus se indica el código sin tener que usar ResponseEntity:

java

public class RecursoNonAtopadoException extends RuntimeException {
    public RecursoNonAtopadoException(String message) { super(message); }
}

// En el servicio:
return userRepository.findById(id)
    .orElseThrow(() -> new RecursoNonAtopadoException("O usuario co ID " + id + " non foi atopado."));

// En el GlobalExceptionHandler:
@ExceptionHandler(RecursoNonAtopadoException.class)
@ResponseStatus(HttpStatus.NOT_FOUND)
public ErrorMessage handleRecursoNonAtopado(RecursoNonAtopadoException ex) {
    return new ErrorMessage(ex.getMessage(), LocalDateTime.now());
}

Manejo a nivel de controlador. Si un error solo afecta a un controlador, se puede poner @ExceptionHandler dentro de ese controlador. Spring prioriza el handler local antes de buscar el global:

java

@RestController
@RequestMapping("/api/usuarios")
public class UsuarioController {
    @ExceptionHandler(IllegalArgumentException.class)   // solo para este controlador
    public ResponseEntity<String> handleInvalidArguments(IllegalArgumentException ex) {
        return new ResponseEntity<>("Erro de argumento: " + ex.getMessage(), HttpStatus.BAD_REQUEST);
    }
}

Esto enlaza con el tema 3: lo ideal es que estos handlers devuelvan los errores en el formato RFC 7807 y con el 4XX más específico, para minimizar los 5XX.

P.11 Cómo encaja todo: el recorrido de una petición

Para ver cómo se combinan las piezas, este es el camino de un POST /api/usuarios en un proyecto típico:

  1. La petición llega al controlador (@RestController + @PostMapping), que convierte el cuerpo JSON en un objeto (@RequestBody, Jackson).
  2. @Valid comprueba las reglas (Hibernate Validator); si fallan, salta MethodArgumentNotValidException y la recoge el @RestControllerAdvice, que responde 400 con el detalle.
  3. Si es válido, el controlador llama al servicio (@Service, inyectado por DI), que aplica la lógica de negocio dentro de una transacción (@Transactional).
  4. El servicio usa el repositorio (JpaRepository o MongoRepository) para guardar en la base de datos: Spring Data JPA llama a JPA, Hibernate genera el INSERT y el driver JDBC lo envía a PostgreSQL, que corre en su contenedor Docker.
  5. El controlador devuelve un ResponseEntity con 201 Created, la cabecera Location y el recurso, serializado por Jackson (respetando @JsonIgnore, @JsonView...).

P.12 Guía: pasos para construir la aplicación

Con todas las piezas vistas, este es un orden razonable para desarrollar la práctica desde cero:

  1. Crea el proyecto con Spring Initializr usando Gradle - Groovy y las dependencias Spring Web, Spring Data JPA, PostgreSQL Driver y Validation (P.1.5, P.1.6).
  2. Levanta la base de datos con el docker-compose.yml y docker compose up -d (P.2).
  3. Configura la conexión en application.properties y arranca la aplicación vacía para comprobar que conecta (P.4.6).
  4. Diseña el modelo E/R y pásalo a relacional (P.4.3).
  5. Escribe las entidades, empezando por las que no dependen de otras y añadiendo después las relaciones. Arranca y comprueba con show-sql o con psql/pgAdmin que las tablas salen como esperabas (P.4.4, P.4.5, P.2.5).
  6. Crea un repositorio (JpaRepository) por cada entidad principal (P.4.8).
  7. Carga datos de prueba con data.sql o CommandLineRunner (P.4.7).
  8. Escribe los servicios (@Service) con la lógica de negocio y @Transactional (P.4.8).
  9. Crea los DTOs para no exponer las entidades directamente y evitar los bucles al serializar (P.4.9).
  10. Escribe los controladores (@RestController) con sus endpoints y ResponseEntity (P.3).
  11. Añade la validación (@Valid, @NotBlank...) y el @RestControllerAdvice para los errores (P.9, P.10).
  12. Por último, lo avanzado si lo pide la práctica: filtros (P.5), paginación (P.6), PATCH (P.7) y vistas con Jackson (P.8).

Una entidad cada vez En lugar de escribir todas las entidades de golpe, haz **una completa de arriba abajo** (entidad → repositorio → servicio → controlador), pruébala con Postman y luego repite con la siguiente. Los errores aparecen antes y es más fácil saber de dónde vienen.

P.13 Ideas clave

  • IoC: Spring crea y gestiona los objetos (beans); DI: las clases declaran lo que necesitan y Spring se lo inyecta (@Autowired, constructor).
  • Spring Boot: convención sobre configuración; servidor embebido (.jar), autoconfiguración, starters. Proyectos nuevos con Spring Initializr (Spring Web + Spring Data).
  • Gradle es el gestor de dependencias: en build.gradle se declaran las librerías (implementation, runtimeOnly, developmentOnly, testImplementation...) y él las descarga con sus dependencias transitivas, compila y empaqueta. Se usa a través del wrapper (./gradlew bootRun, ./gradlew build).
  • Docker ejecuta programas en contenedores ligeros creados a partir de imágenes; con Docker Compose (docker-compose.yml + docker compose up -d) se levanta PostgreSQL con su base de datos, puertos mapeados y un volumen para los datos. Las VMs simulan un ordenador completo, Kubernetes orquesta muchos contenedores y AWS es infraestructura alquilada.
  • Capas: @RestController (sin lógica) → @Service (lógica) → @Repository (datos).
  • REST: @RequestMapping (ruta base), @GetMapping/@PostMapping/@PutMapping/@PatchMapping/@DeleteMapping; datos con @PathVariable (path), @RequestParam (query), @RequestBody (cuerpo); códigos con ResponseEntity.
  • JPA = especificación, Hibernate = implementación, Spring Data JPA = repositorios automáticos. @Entity; relaciones @ManyToOne (propietario, FK, poner LAZY), @OneToMany(mappedBy), @OneToOne, @ManyToMany(@JoinTable). Evitar N+1 con JOIN FETCH/@EntityGraph; devolver DTOs.
  • Cadena de una operación: Spring Data JPA → JPA (EntityManager) → Hibernate (genera SQL) → driver JDBC → base de datos. Spring Boot ejecuta data.sql; Hibernate no.
  • Diseño: E/R → relacional → clases @Entity; no se escribe CREATE TABLE, las tablas las crea Hibernate con spring.jpa.hibernate.ddl-auto (create, update, validate...). Datos iniciales con data.sql (+ defer-datasource-initialization=true y sql.init.mode=always), CommandLineRunner o la propia API.
  • Filtros dinámicos: Query By Example (+ ExampleMatcher) o Criteria/Query (MongoTemplate).
  • Paginación: Pageable/Page (total, pero recuento extra e inconsistencias) o cursores (eficiente, sin saltar páginas).
  • PATCH con JSON Patch (op, path, value): obtener → a JsonNode → aplicar → a objeto → guardar.
  • Jackson: @JsonInclude(NON_NULL), @JsonIgnore, @JsonProperty, @JsonFormat, @JsonView.
  • Validación: anotaciones (@NotBlank, @Size, @Email...) + @Valid en el @RequestBody → MethodArgumentNotValidException → 400.
  • Errores: @RestControllerAdvice + @ExceptionHandler, excepciones propias y @ResponseStatus; el handler local tiene prioridad sobre el global.

Anexo A. Git: borrar el historial y el repositorio remoto

A veces se quiere empezar el historial de cero: por ejemplo, porque se subió por error una contraseña (típico en application.properties) o porque el historial está lleno de pruebas. Antes de nada, tres avisos:

  • Estas operaciones reescriben la historia y no se pueden deshacer en el remoto. Haz antes una copia de la carpeta del proyecto.
  • Si trabajas con más gente, sus copias locales dejarán de cuadrar con la tuya y tendrán que volver a clonar.
  • Si el motivo es una contraseña o clave subida, borrar los commits no basta: alguien pudo verla o clonarla, y GitHub puede conservar copias en caché un tiempo. Cámbiala igualmente.

A.1 Conservar los archivos y dejar un único commit

Opción 1: rama huérfana (recomendada). Una rama huérfana nace sin ningún commit anterior. Se crea una, se meten en ella los archivos actuales y se sustituye la rama principal:

bash

git checkout --orphan nueva-rama      # rama nueva sin historial (conserva tus archivos)
git add -A                            # añade todos los archivos
git commit -m "Commit inicial"        # el único commit que quedará
git branch -D main                    # borra la rama main antigua
git branch -m main                    # renombra la nueva rama a main
git push -f origin main               # sube y SOBRESCRIBE el remoto

El -f (force) obliga al remoto a aceptar la nueva historia en lugar de la antigua; sin él, rechaza el push. Si la rama principal se llama master, cambia el nombre en los comandos (compruébalo con git branch).

Opción 2: borrar la carpeta .git. Todo el historial vive en la carpeta oculta .git; si se borra, el proyecto deja de ser un repositorio y se puede inicializar de nuevo:

bash

rm -rf .git                                   # Linux/Mac
# Remove-Item -Recurse -Force .git            # PowerShell (Windows)

git init
git add -A
git commit -m "Commit inicial"
git branch -M main
git remote add origin https://github.com/TU_USUARIO/TU_REPO.git
git push -f -u origin main

Es más directo, pero se pierde también la configuración local del repositorio (por eso hay que volver a añadir el remoto).

Ambas opciones solo limpian main. Si en el remoto hay otras ramas o etiquetas, siguen ahí con su historial antiguo. Se listan con git branch -r y git tag, y se borran con:

bash

git push origin --delete nombre-de-la-rama
git push origin --delete nombre-del-tag

A.2 Borrar el repositorio remoto entero

Git no puede borrar un repositorio remoto: solo sube y baja commits. Hay que hacerlo en GitHub (o donde esté alojado):

  • Desde la web: en el repositorio, Settings → al final, Danger Zone → Delete this repository, y confirmar escribiendo el nombre completo (usuario/repo). En repositorios de una organización hace falta ser administrador.
  • Desde la terminal, con GitHub CLI: gh repo delete usuario/repo. Si avisa de que falta el permiso, se concede con gh auth refresh -h github.com -s delete_repo.

Es definitivo: se borran también las issues, pull requests, wiki y estrellas. Los forks que otras personas hubieran hecho siguen existiendo, porque son copias independientes en sus cuentas.

Después, en tu ordenador, la carpeta sigue intacta pero apunta a un remoto que ya no existe. Quita la referencia con git remote remove origin y decide:

  • Volver a subirlo limpio: crea un repositorio nuevo vacío en GitHub y sigue la opción 2 de A.1 con la nueva URL. Es la forma más limpia de eliminar por completo un historial con credenciales.
  • Quedarte sin Git: borra también la carpeta .git. Los archivos se quedan, sin historial.

A.3 Que no vuelva a pasar: contraseñas fuera de Git

En lugar de escribir la contraseña en application.properties, se puede leer de una variable de entorno, con un valor por defecto para desarrollo:

properties

spring.datasource.password=${DB_PASSWORD:postgres}   # usa DB_PASSWORD si existe; si no, "postgres"

Otra opción es poner los valores sensibles en un fichero aparte (por ejemplo, application-local.properties) y añadirlo al .gitignore.
